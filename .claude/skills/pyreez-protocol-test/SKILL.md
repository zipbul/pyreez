## 무엇을 / 왜

프로토콜 프롬프트의 품질은 **읽어서 판단할 수 없다.** 같은 프롬프트가 모델·런마다 다른 행동을 내고(temp=1.0), 사람이 "괜찮아 보인다"고 한 조항이 실제로는 환각을 유발하기도 한다. 이 스킬은 판단을 **"프롬프트 조항 → 워커의 실제 행동" 인과**로 환원한다: 실제로 렌더하고, 실제로 돌리고, 출력을 한 줄씩 의심하고, 워커 본인에게 왜 그렇게 했는지 캐묻고, 측정된 결함만 고친다.

핵심 규율 두 개:
- **추측 금지.** 프롬프트가 무엇을 유발할지 상상하지 말고 실행해서 관측한다.
- **"할 만큼" 금지.** 매 런 결함이 나온다. 결함이 줄지 않으면 "충분하다"가 아니라 레버를 덜 돌린 것이다 (아래 레버 우선순위).

## 고정 태스크 세트

매 측정은 **동일한 N개 다양성 태스크**로 돈다(런 간 비교 가능성 확보). 도메인을 분산: 동시성/멱등성, 빌드·CI, 데이터스토어, 인증/보안, 분산 스트리밍, 프레임워크 의미론 등. 최소 6개 권장. 세트를 한 번 정하면 버전 비교 내내 고정한다 — 태스크를 바꾸면 결함률 비교가 무의미해진다.

## 절차 (순서 강제)

### 1. RENDER — 워커에 가는 풀 프롬프트를 그대로 뽑는다
추정하지 말고 렌더러로 실제 문자열을 출력한다.
```bash
bun run scripts/dump-protocol-prompts.ts   # 프로토콜별 system + 라운드별 user turn 렌더
```
system 블록과 각 라운드 user turn을 분리해 확보한다. 이게 이후 모든 "어떤 조항 탓인가" 추적의 기준선이다.

### 2. RUN + CAPTURE — 라이브 실행해 과정·결과를 전부 잡는다
```bash
bun run src/cli.ts deliberate \
  --task "<고정 태스크>" --models "<m1,m2,m3>" --protocol <protocol> \
  --max-rounds <N> [--web-access true] [--reasoning-effort 1..10] > capture.json
```
출력 JSON에서 **과정 = `rounds[].responses[].content`** (라운드별·워커별), **결과 = synthesis/최종 출력**. 라운드·모델별로 텍스트를 분리 저장한다(`r<round>_<model>.txt`). temp=1.0이라 런마다 산출물이 다름을 전제 — 결론은 단일 런이 아니라 세트 전체에서.

### 3. LINE-BY-LINE 의문 — 과정/결과를 한 줄씩 의심한다
각 출력 줄에 대해 두 질문을 강제한다:
- **"왜 이렇게 출력했나?"** (행동의 원인)
- **"어떤 프롬프트 조항이 이 결과를 유발했나?"** (조항→행동 매핑; RENDER 기준선과 대조)

여기서 결함 후보가 나온다. 인상이 아니라 **출력 텍스트의 정확한 인용**으로 기록한다.

### 4. SAME-SESSION INTROSPECT — 워커 본인에게 캐묻는다
빌트인 커맨드가 아니다. 워커 세션을 재구성해 직접 묻는다: 그 모델에 `[원래 system, 원래 user turn, assistant: 워커의 실제 출력, user: "너는 X라고 출력했다. 왜인가? system/지시의 어떤 부분이 이걸 시켰나? 그게 없었다면 달리 했겠나?"]` 형태의 대화를 다시 태운다. 호출 방식은 실행 전 `src/llm/providers/`에서 해당 프로바이더의 세션-이어가기 방식을 확인하고 맞춘다(추측 금지). 워커 본인의 인과 진술로 3단계 가설을 검증/반증한다.

### 5. 삼자 교차리뷰 — 나 + 서브에이전트 + codex
**pyreez deliberation이 아니다.** {풀 프롬프트 + 모든 과정/결과 출력}을 세 주체가 독립적으로 본다: 본인(메인 루프), general-purpose 서브에이전트, `codex:codex-rescue`. 한 모델의 "이상 없음"은 한 표일 뿐 — 합의로 수렴을 조작하지 말고 각자가 새 결함을 가져오게 한다. 서브에이전트/codex 결과는 입력이지 결론이 아니다 — 본인이 코드·웹으로 재검증 후 채택.

### 6. VERIFY + QUANTIFY — 모든 사실주장 검증, 결함 분류
워커가 낸 모든 사실 주장(인용·식별자·수치·API·기본값)을 웹/코드로 직접 확인한다. 결함을 클래스로 분류해 정량화한다. **결함률 = 결함 수 / 총 검증가능 주장 수.**

| 결함 클래스 | 정의 |
|---|---|
| fabricated | 존재하지 않는 사건/출처/사고를 지어냄 (치명적) |
| misattributed | 실재하나 잘못된 주체/맥락에 귀속 |
| fake-id | 존재하지 않는 명령/플래그/API/설정키 |
| paraphrase-as-quote | 의역을 직접 인용처럼 표기 |
| number-wrong | 출처와 다른 수치/기본값 |
| abstention | `[unverified]` 등으로 정직하게 보류 (결함 아님 — 측정 대상) |

### 7. FIX + REMEASURE — 재현된 결함만 고치고 효과를 증명
- 3~6에서 **재현된** 결함만 프롬프트로 수정한다. 인상·이론만으로 고치지 않는다.
- 수정 후 **같은 고정 세트로 재측정**해 결함률 변화를 수치로 보인다.
- 효과가 측정되지 않으면(노이즈 내) **변경을 회수**한다.
- 룰 추가가 다른 결함 클래스로 트레이드되는지 확인 — 한 클래스를 줄이며 다른 클래스를 늘리면 순이득 0.

## 레버 우선순위

프롬프트 룰로 안 내려가는 잔여(정밀도 결함, confident-wrong-recall)는 **룰을 더 쌓지 말 것** — 측정상 한 클래스를 다른 클래스로 옮길 뿐이다. 대신 벤더 레버를 돌린다:
1. **reasoning-effort** (`--reasoning-effort 1..10`) — 추론 깊이. 프롬프트에 추론 지시를 박지 말고 이 파라미터를 쓴다.
2. **web-access / tool-grounding** (`--web-access true`) — 워커가 인용을 기억이 아니라 실제 조회로 검증. confident-wrong-recall 잔여의 유일한 입증된 레버. 비용·지연 ~2-3× — caller opt-in.

프롬프트는 "측정된 한계"까지만 밀고, 그 아래는 레버로.

## 통계 정직성

- n, 단일 판정자 한계, Wilson CI 겹침을 항상 명시한다. n=6 수준은 underpowered — 결론은 "통계적으로 입증" 아니라 "방향성"으로 라벨.
- 메트릭으로 결론 내기 전 **inter-rater 신뢰도(κ)를 먼저 확인**한다. 부적절·주관적 메트릭은 κ가 무너져 거짓 천장 결론을 낳는다(base-rate가 한쪽으로 쏠리면 kappa-paradox로 κ가 0에 붙어도 raw agreement는 높을 수 있음). 객관·규칙일치 메트릭을 써라.

## 산출물

프로토콜별 `docs/protocol-prompts/<protocol>/STATUS.md`:
- 버전별 결함률 표 (버전 | 프롬프트 변경 | 결함률 | 클래스별 카운트 | 추론품질 | 보류수).
- 측정 저널 (각 캠페인의 n·모델·검증방식, 회수된 변경 포함).
- 천장 (근거 기반 — 무엇이 해결됐고 무엇이 잔여이며 왜인지).
- 열린 항목.

스크래치(캡처 JSON, 라운드별 txt, introspect 로그)는 gitignore 경로(`.advreview/` 류)에. `STATUS.md`만 docs에 커밋.

## 금지

- 코드/스킬/프롬프트에 academic citation·내부 버그ID·file:line 인용 박지 말 것 — 소비 에이전트의 행동을 바꾸는 정보만.
- gap 미검증 "완료" 선언 금지. 미검증 항목을 list화 → 검증 → 잔여 0 후 보고.
- 스킬에 적은 명령어가 리포 현실과 다르면 실행 전 확인 후 정정. 명령어를 신뢰하지 말고 검증하라.
