**Condition 1: Weekly Non-Backward-Compatible Schema Changes + <1 FTE DevOps Capacity**

**Steelman:** PostgreSQL's schema-first model is an asset for mature products; for unproven MVPs, frequent pivots in data structure are inevitable, and each change requires a blocking migration—downtime, rollback procedures, coordination tax. MongoDB's flexible schema lets the team ship schema mutations without ceremony.

**Weakness:** If the product domain is novel (new creator tool, vertical SaaS in unfamiliar domain) and the 4-person team learns, weekly, that their data model was wrong—e.g., user profile structure needs nesting, event payload needs new optional fields, or a core entity must split into two—each PostgreSQL change becomes a migration task. Even with 0-downtime strategies (new column, dual-write, backfill, drop), the QA and coordination cost is ~2–3 hours per migration [unverified estimate]. A 4-person team split across frontend, backend, product, and ops has ~1 person-week of DevOps slack. Two migrations per sprint quickly exhausts it, and the team starts deferring data structure improvements to cut scope. MongoDB allows both shapes to coexist in the same collection; new code writes the new shape; old code still works. This is less risky and faster to ship.

**Evidence:** PostgreSQL ALTER TABLE is a blocking operation on large tables; Postgres rewrites the table under most DDL operations (exceptions exist but require version-specific knowledge). A 4-person team without dedicated DevOps is unlikely to have expertise in zero-downtime migration strategies (logical replication, dual schema, etc.). The time tax is real: schema review → test migration → apply → verify → rollback procedure. MongoDB's schema flexibility is built-in, not an afterthought.

**Falsification:** Measure actual schema-change frequency over 3 months post-launch. If <1 major non-backward-compatible change per sprint, PostgreSQL's rigidity is irrelevant. If >3 per sprint *and* the team reports migration overhead as a blocker (explicit quotes like "we delayed feature X because of schema work"), the condition holds. Interview DevOps person on time spent on migrations.

**Verdict:** **HIGH severity, MEDIUM confidence.** Real for novel products, but contingent on rapid pivots being actual, not hypothetical. Weak for product categories with stable models (e.g., e-commerce checkout).

---

**Condition 2: Write-Heavy Workload on a Small Hot Set with Loose Consistency Tolerance (Leaderboard, Shared Inventory, Notification Queue)**

**Steelman:** PostgreSQL's row-level locks and serialization guarantees deliver value only if the workload is read-dominant or strict consistency is required. Some MVP use cases—real-time ranking, shared resource pools, high-frequency activity feeds—are write-heavy on a small dataset, where PostgreSQL's lock serialization creates contention and tail latency spikes.

**Weakness:** If the MVP's primary loop is many concurrent writes to few rows (e.g., 100+ concurrent clients incrementing a leaderboard, tens of thousands of events appended to a user's feed per minute, or N workers decrementing a shared ticket inventory), PostgreSQL's row-level locking forces a queue: lock wait time grows with contention. MongoDB's sharding distributes the hot set across multiple leaders; conflict rates are lower (no row lock, just version checks). Benchmarks typically show MongoDB throughput 2–10x higher under this access pattern [unverified; direction is well-established in DB literature]. For an MVP with a bursty viral moment (product launch, social media spike), PostgreSQL's p99 latency can jump from 50ms to 500ms+ when the hot set lock queue fills. MongoDB's tail latency remains flatter because lock contention is distributed. This kills user experience at the moment of peak visibility.

**Evidence:** PostgreSQL uses shared/exclusive row locks; under concurrent writes to the same rows, lock-wait time becomes the primary latency component. This is a known tradeoff: PostgreSQL prioritizes consistency, MongoDB prioritizes availability. MongoDB's sharding (if configured), plus eventual consistency for counter operations, allows faster writes. The downside: lost updates or stale reads are possible without application-level conflict resolution, but most leaderboards and activity streams tolerate this.

**Falsification:** Simulate your actual write pattern (concurrency level, rows touched per operation) on both databases. Measure p99 write latency and throughput under realistic peak load (e.g., 1 million operations/hour). If PostgreSQL p99 is >2x MongoDB's, the condition holds and the user experience degrades. If both are <100ms p99, PostgreSQL's consistency wins and this weakness doesn't manifest.

**Verdict:** **HIGH severity, MEDIUM confidence.** Real tradeoff, but only manifests for specific workload shapes. Many SaaS MVPs are read-dominant (dashboards, content discovery), so this doesn't apply. If your MVP is a real-time game, activity feed, or marketplace with high write churn, this is material.

**Condition 3: Team Lacks Relational Modeling Expertise (Majority Node/React Background, No Prior SQL Work)**

**Steelman:** PostgreSQL's power comes from disciplined schema design and SQL's expressiveness. A team unfamiliar with normal forms, foreign keys, and join optimization will make costly mistakes: over-normalization, N+1 queries, inefficient index strategies. MongoDB's nested documents feel more natural to JavaScript-first developers and reduce the barrier to productive database work.

**Weakness:** If the team is 3 JavaScript developers + 1 generalist, with no prior relational DB design experience, the ramp-up cost to write a good PostgreSQL schema is real. They will bikeshed over whether to normalize or denormalize, struggle with junction tables, and discover N+1 query bugs in production. Each discovery costs a sprint's worth of refactoring. MongoDB's document model maps directly to JavaScript objects and JSON API responses; new developers can reason about queries faster (`.find({ userId: id })` is more intuitive than multi-table joins). For a 6-month MVP, a 2–4 week ramp-up delay [unverified estimate] represents 8–13% of the runway—significant for a 4-person team. Additionally, every new team member (contractor, hire) faces the same ramp-up cost with PostgreSQL; MongoDB's schema-as-you-go model has a shallower learning curve.

**Evidence:** Anecdotal from retrospectives and hiring feedback; JavaScript developers often find SQL unintuitive on first exposure (joins, aggregation pipelines, index design). No quantitative study recalled. The cognitive load of relational thinking is well-documented in pedagogy: nested documents (MongoDB) align with object-oriented thinking; relational decomposition (PostgreSQL) requires a mental model shift. A 4-person team without a strong DBA will optimize sub-optimally.

**Falsification:** Audit the team's first 10 production queries (SQL for PostgreSQL, aggregation pipelines for MongoDB). Count N+1 queries, missing indexes, or inefficient joins in PostgreSQL; count equivalent issues in MongoDB. If PostgreSQL queries are >30% less optimal (e.g., more full-table scans, more network round-trips), and the team reports that schema design felt harder, the condition holds. If the team navigates PostgreSQL confidently, this weakness is irrelevant.

**Verdict:** **MEDIUM severity, MEDIUM-HIGH confidence.** Realistic scenario (many startups are JS-first), real friction, but not insurmountable. Training, ORMs, and schema scaffolding tools (Prisma, migrations) mitigate the risk. However, they add overhead—the team must adopt them, learn them, and maintain them.

**Synthetic fourth candidate (low severity, kept for completeness):**

**Condition 4: Rapid API Evolution and Multi-Version Support Without Schema Versioning**

If the MVP must support multiple API versions concurrently (e.g., web v1, mobile v2), PostgreSQL forces schema versioning or application-layer mapping. MongoDB allows both document shapes to coexist in the same collection, reducing coordination. However, this is rare for 6-month MVPs (version support is a later-stage problem). **Verdict: LOW severity, LOW confidence.** Ruled out as contingency.

---

**Summary—Conditions Under Which PostgreSQL is Worse:**

1. **Weekly schema pivots + DevOps understaffed** → schema-change overhead dominates
2. **Write-heavy hot-set workload** → lock contention kills p99 latency
3. **Team skews JavaScript, no SQL experience** → ramp-up and suboptimal query design consume runway

**Condition for Acceptability:** PostgreSQL remains the right choice if the team has relational DB expertise, the workload is read-heavy or loosely coupled, and the schema stabilizes within 2 weeks. **If none of the three conditions above hold, PostgreSQL's long-term benefits (consistency, tooling, ecosystem) outweigh MongoDB's short-term friction.**
