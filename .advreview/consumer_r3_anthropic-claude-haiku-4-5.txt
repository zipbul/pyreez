## Surviving Findings (Severity-Ordered)

### **1. Polymorphic or Tenant-Variable Schema is Central to the Product**

**Weakness:** PostgreSQL is strictly worse when the MVP's core entities intentionally have heterogeneous shape across tenants, integrations, customer-defined fields, or versioned object variants that must all remain queryable. The team either burns time on repeated migrations for each variant (relational approach), or pushes variance into JSONB and loses schema clarity and queryability (JSONB approach). MongoDB allows optional fields with conditional validation, so variants coexist naturally without schema rewrites or runtime type-checking in application code.

**Evidence:** MongoDB's schema validation documentation explicitly shows optional fields with conditions ("'gpa' must be a double if the field exists"). PostgreSQL's JSON guidance recommends "somewhat fixed structure," meaning a schema-per-variant in relational form or a validation-at-runtime in application code with JSONB. The core mechanism is verified: PostgreSQL's default assumption is a fixed column set; MongoDB's is optional fields and conditional rules.

**Falsification:** List all planned sources of schema variation (tenant custom fields, integration payloads, versioned entities, etc.). If the non-uniform part is genuinely small and opaque—stored as blobs, rarely filtered, never joined on—PostgreSQL absorbs them without friction. If &gt;30% of queries filter or join on variable fields, PostgreSQL becomes operationally costly.

**Verdict:** HIGH severity | MEDIUM confidence

---

### **2. Dominant Access Pattern is Read/Write of Bounded Nested Aggregates**

**Weakness:** PostgreSQL is strictly worse when the workload revolves around reading and writing a self-contained nested object as an atomic unit—workflow definitions, onboarding state, config documents, generated manifests—and cross-aggregate joins are rare. MongoDB's document model is the native storage primitive for that access pattern. PostgreSQL either stores it as JSONB (paying a row-level lock on the entire aggregate for any update) or normalizes it (adding join overhead for every read). Neither path avoids friction that MongoDB avoids.

**Evidence:** MongoDB docs confirm single-document atomicity and recommend embedding for data that is "accessed together"; PostgreSQL docs warn that "any update to a JSON document acquires a row-level lock on the whole row" and recommend limiting document size to "decrease lock contention." The mechanism: aggregate-scoped workload → MongoDB stores it atomically → simple read/write paths; PostgreSQL either serializes concurrent updates to one row or fractures the aggregate into joins.

**Counter-evidence (narrows but does not refute):** If the aggregate grows unbounded or cross-aggregate filtering emerges, MongoDB's 16 MB document limit forces extraction of sub-collections, and cross-collection queries require `$lookup` pipelines that are harder to reason about than SQL JOINs. However, within the MVP 6-month window and before significant data accumulation, this is unlikely to emerge.

**Falsification:** Sample the top 20 reads and writes. If &gt;30% involve joins across independent entities or multiple actors updating different subparts concurrently, MongoDB's advantage narrows. If &lt;10% do, the finding holds.

**Verdict:** HIGH severity | MEDIUM confidence

---

### **3. Schema Changes Involve Non-Additive DDL on Hot Tables During Discovery**

**Weakness:** PostgreSQL incurs operational friction when product discovery requires frequent non-additive changes—renaming columns, changing field types, adding NOT NULL constraints to populated columns—on tables that already receive live traffic. These operations trigger `ACCESS EXCLUSIVE` locks and potentially full table rewrites. The rewrite time depends on table size; at MVP scale (hundreds of thousands to low millions of rows), rewrites take seconds to minutes, during which the table is locked and reads/writes queue behind the DDL.

MongoDB avoids this because product iteration can ship as application-level shape changes with optional fields; validation is applied only to new data or when the schema stabilizes.

**Evidence:** PostgreSQL docs confirm that renaming a column, changing a column type, or adding a NOT NULL constraint (after population) all require table rewrites. Xata.io and GoCardless post-mortems confirm that lock cascades occur when DDL queues behind existing queries. The mechanism is verified: non-additive DDL → exclusive lock + potential rewrite → query queue formation.

**Counter-evidence (narrows but does not refute):** If the team's schema iterations are mostly additive—adding nullable columns, adding columns with non-volatile defaults—those operations complete in milliseconds (catalog-only metadata updates, no table rewrite) even on large tables. At MVP scale in the first 6 months, additive changes likely dominate. The finding fires only when non-additive changes are frequent.

**Falsification:** Classify the next 8 weeks of expected model changes. If &gt;30% are non-additive (type changes, constraint additions requiring scans, renames), the finding holds. If &lt;10%, the migration cost is near-zero and the finding drops to low confidence.

**Verdict:** MEDIUM severity | MEDIUM confidence

---

### **4. Serverless or Function-as-a-Service Deployment Model**

**Weakness:** PostgreSQL requires long-lived connection pooling (PgBouncer, RDS Proxy, or similar) and persistent server processes to avoid connection-creation overhead and keep connection counts within limits. Serverless functions (AWS Lambda, Google Cloud Functions) create transient short-lived connections, which PostgreSQL handles poorly—each function invocation must acquire a new connection, and the pooling layer must be external. MongoDB Atlas also requires pooling but is more forgiving of short-lived connections in its serverless tier (and developers are accustomed to designing no-SQL applications for that constraint).

**Evidence:** PostgreSQL docs recommend keeping connection count low; each connection consumes ~10 MB of memory by default. RDS connection limits on small instances (db.t3.micro has 20 connection limit) leave little headroom for a Lambda application spawning workers. MongoDB Atlas serverless explicitly supports transient, stateless functions. Mechanism: serverless architecture → stateless, short-lived connections → connection pool contention for PostgreSQL; MongoDB handles this as a designed constraint.

**Falsification:** If the deployment is a persistent application server (EC2, container, or dedicated RDS), PostgreSQL's connection model is not a friction point. If the team plans serverless, benchmark connection creation latency and pool wait times under a realistic Lambda concurrency model. If p99 latency degradation &gt;100ms due to connection pool wait, the finding holds.

**Verdict:** MEDIUM severity | MEDIUM confidence (conditional on serverless choice, which is not stated in the problem)

---

### **5. Write-Heavy Workload with Large JSONB Documents**

**Weakness:** If the application stores large JSONB blobs (several MB per row) and the workload is write-heavy with frequent concurrent updates to the same document, PostgreSQL's row-level locking on JSONB updates serializes concurrent mutations. MongoDB's BSON model with field-level mutations and higher write throughput (per the Binary Igor and MongoDB engineering benchmarks, though with caveats) may outperform PostgreSQL's approach.

**Evidence:** PostgreSQL docs state that JSONB updates acquire row-level locks on the entire row. MongoDB's write model is optimized for concurrent document updates. The Binary Igor benchmark showed MongoDB 4.14× advantage on sorted pagination and 42% on batch inserts, though with configuration asymmetries (4× connection slots, 3× cache for MongoDB).

**Counter-evidence (narrows confidence substantially):** The Binary Igor asymmetry (MongoDB 256 connections vs PostgreSQL 64, MongoDB 12 GB cache vs PostgreSQL 4 GB) makes the 4× figure unreliable. Rerunning with matched resources would be the proper test. Additionally, the MongoDB engineering benchmark auto-scaled MongoDB mid-test while PostgreSQL remained fixed, measuring resource exhaustion, not architecture. At MVP scale with proper connection pooling and cache sizing, PostgreSQL's JSONB performance may be adequate.

**Falsification:** Benchmark the actual expected write pattern (document size, update frequency, concurrency) on both databases with matched hardware and connection pool sizing. If PostgreSQL's p99 write latency exceeds MongoDB's by &gt;2× at the same concurrency level, the finding holds. If the gap is &lt;20% or can be closed with connection pool tuning, PostgreSQL remains viable.

**Verdict:** MEDIUM severity | LOW confidence (because the benchmark evidence is asymmetric and the magnitude is unquantified for MVP-specific workloads)

---

### **6. Team Lacks PostgreSQL Operational Expertise and No Managed Service is Available**

**Weakness:** If the team must run PostgreSQL on self-managed infrastructure (bare VMs, on-prem) without access to managed services (RDS, Supabase, Neon, Render) and no team member has experience with vacuum, autovacuum tuning, or query plan analysis, operational surprises can burn engineering time. Autovacuum misconfiguration, transaction ID wraparound, or untuned query plans can degrade performance gradually, and the debugging cost falls on a 4-person team with no margin.

MongoDB Atlas offers more visibility and less tuning, especially for early-stage MVPs; it abstracts operational complexity.

**Evidence:** PostgreSQL requires understanding vacuum cycles, autovacuum settings, and long-running transaction impacts. Managed PostgreSQL services (RDS, Supabase, Neon) all expose these via dashboards. MongoDB Atlas similarly abstracts operations but is marketed as simpler for teams new to databases. Mechanism: self-managed infrastructure + no expertise → slow performance degradation → unfamiliar debugging surface → sunk engineering time.

**Counter-evidence (strongly narrows):** If the team uses a managed service (which is the standard for MVP launches), this weakness evaporates. RDS, Supabase, and Neon all ship with autovacuum pre-tuned and monitoring dashboards. The problem statement does not mention self-managed infrastructure, and launching an MVP on self-managed Postgres without DBA support is an unforced choice.

**Falsification:** Confirm deployment strategy. If the team commits to a managed PostgreSQL service with monitoring (RDS, Supabase, Neon, Render), this weakness is moot. If self-managed, hire or train one team member on autovacuum basics, or upgrade to managed within month 1. If neither happens and performance degrades unexpectedly, the finding holds.

**Verdict:** LOW severity | MEDIUM confidence (conditional on a deployment choice not stated in the problem)

## Final Acceptability Condition

PostgreSQL is the acceptable default if **at least four of the following six conditions hold**:

1. Core domain entities have stable, known schemas expressible in an ER diagram before month 1 (variant shapes are &lt;30% of entities or are non-queryable blobs).
2. Primary access patterns are relational—entities are joined, filtered, and aggregated across boundaries; single-aggregate reads/writes are &lt;10% of the workload.
3. Product discovery model changes are expected to be mostly additive (nullable columns, new tables, new columns with defaults) rather than type changes, constraint additions on populated columns, or renames.
4. Deployment is a persistent application server (EC2, container, dedicated RDS instance) or a managed PostgreSQL service (RDS, Supabase, Neon, Render), not serverless functions.
5. At least one team member has read `EXPLAIN ANALYZE` output or the team uses a managed PostgreSQL service with monitoring dashboards.
6. Write-heavy JSONB workloads, if present, are either small documents (&lt;100 KB per row) or lightly concurrent (no more than 10% of operations are concurrent updates to the same row).

**If three or more of these conditions fail, or if finding #1 or #2 applies at full strength, a 2-day spike with both PostgreSQL and MongoDB against the actual top-10 queries is required before committing.** Absent that validation, the evidence in this record does not support calling PostgreSQL strictly worse at the outset; it supports treating the choice as underdetermined.
