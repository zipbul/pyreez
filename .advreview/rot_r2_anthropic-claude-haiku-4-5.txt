**Rapid, unplanned schema evolution in the first 3–4 months**

target: Analyst A, Analyst B

steelman: PostgreSQL's required explicit migrations and schema planning create coordination overhead during the MVP's most volatile discovery phase; MongoDB's schema-on-read model allows the same data-model changes with atomic document updates.

weakness: If the core entity structure pivots mid-development (e.g., single-user to multi-tenant by month 3, or permissions model reshapes from columns to tables), PostgreSQL forces explicit ALTER TABLE + coordinated testing + rollback planning. Under deadline pressure with poor upfront schema discovery, cumulative coordination cost (testing, validation, rollback contingency) can exceed MongoDB's application-layer schema validation overhead. Analyst B claims migrations cause "downtime," but modern zero-downtime techniques (pg_partman, logical replication) mitigate this; the real cost is developer coordination, not storage unavailability. However, if the team front-loads schema discovery (weeks 1–2) and locks the model by month 2, migrations become a one-time cost, not recurring. The condition fires only when schema instability extends through month 4 and the team lacks migration discipline.

evidence: PostgreSQL migration tools (Alembic, Flyway) require version discipline; MongoDB defers validation to application layer (Pydantic, JSON Schema). For a 4-person team under timeline pressure, the bottleneck is not database capability but bandwidth to plan, test, and verify migrations. Analyst B's falsification (measure cycle time for 2 schema changes over 2 weeks) is sound, but may miss costs if migrations happen off-sprint. Real overhead: ALTER TABLE on a growing table blocks or requires careful locking; MongoDB appends/reshapes fields without coordination overhead.

falsification: Instrument a 6-week MVP window with 2–3 unplanned breaking schema changes (e.g., permission model redesign). Measure developer-hours for each: (a) requirement analysis → schema decision, (b) migration code + testing + rollout. If PostgreSQL average per change is < 6 hours and MongoDB is not demonstrably < 3 hours, this condition does not fire. If PostgreSQL averages > 12 hours and the team lacks a migration framework, it does.

verdict: **CRITICAL, MEDIUM.** Highest impact on launch timeline, but condition is narrow: requires both *unplanned* breaking changes *and* weak upfront schema discipline.

**Document-scoped access patterns with negligible cross-entity operations**

target: Analyst A

steelman: When nearly every request reads or writes a single tenant-scoped aggregate (user profile, project metadata, document content) without joins or multi-row transactions, PostgreSQL's relational machinery is unused overhead; MongoDB's document model aligns directly with the access pattern.

weakness: If 95%+ of requests are single-document reads/writes and cross-entity operations (reporting, billing, consistency constraints) are truly negligible at MVP launch, PostgreSQL's relational design buys little while requiring table normalization and JOINs the team never executes. However, most SaaS products evolve by month 4–5 to require cross-entity operations: billing needs to count users per team; reporting needs to correlate events across accounts; batch jobs need multi-record transactional integrity. MongoDB's answer is application-level joins (N+1 queries, manual consistency logic), which is slower and more error-prone than SQL. The condition holds only if cross-entity operations genuinely remain < 5% of code complexity for 12+ months post-launch—rare for SaaS.

evidence: Single-aggregate products exist (document editors where users edit only their own docs, initially). Mongoose maps documents 1:1 with this access pattern; PostgreSQL requires normalization into multiple tables. However, Analyst A's falsification ("inspect endpoint graph") only captures the current MVP state, not future features. A product roadmap introducing collaboration, reporting, or billing will demand joins within 6 months, making PostgreSQL's safety net essential.

falsification: Inspect the current endpoint graph AND product roadmap for 12 months post-MVP. If the top 20 endpoints by projected call frequency have zero joins or multi-row transactions AND the roadmap has no reporting, billing, audit, or collaboration features, this condition holds. Otherwise, PostgreSQL's relational model will be needed.

verdict: **HIGH, MEDIUM.** Real but narrow scope; fires only for single-aggregate products with genuinely flat roadmaps (rare).

**Deeply nested, frequently updated domain structures**

target: Analyst A

steelman: When the MVP's core feature involves a tree or DAG (collaborative document with nested comments, reactions, edit history) that updates atomically, MongoDB's document model allows the entire structure in one document; PostgreSQL forces either multi-table JOINs or JSONB with application-layer schema enforcement.

weakness: A comment thread with 50 replies + reactions + versions is one atomic MongoDB document; in PostgreSQL, it's either a JSONB field (requiring application schema validation + GIN index tuning) or a normalized 4–5 table structure (requiring multi-table transactional integrity on every comment append). For a 4-person team, code complexity of maintaining JSONB schema consistency is a tax on feature velocity. However, Analyst A understates JSONB's capabilities: modern ORMs (Pydantic, SQLAlchemy) reduce this gap by centralizing schema validation once, then reusing it. The condition holds if the team lacks JSONB expertise AND nested updates are a core feature, not a future refinement.

evidence: JSONB + GIN indexes are performant, but they require application-layer schema enforcement; MongoDB's schema validation is built-in. Querying nested JSONB paths is less ergonomic than MongoDB aggregation, but possible. Real friction is developer time on index strategy and validation plumbing, not storage performance. Pydantic (now ~5 years mature) and SQLAlchemy's JSON types have narrowed the asymmetry significantly.

falsification: Prototype both architectures for a nested-tree feature (100-node comment thread, 5+ fields per node, append/edit operations). Measure (a) query latency (avg, p99) for range queries on nested fields, (b) atomic update latency, (c) LOC for schema validation + index management. If PostgreSQL latency ≤5% slower and LOC ≤20% higher, this condition does not fire.

verdict: **MEDIUM, MEDIUM.** Friction is real but mitigated by JSONB and mature ORMs; fires only if nested data is a core feature AND team lacks JSONB expertise.

**High-write, low-consistency event or analytics streams**

target: Analyst B

steelman: When the MVP traffic pattern is dominated by high-write event or analytics streams (millions of impressions, activity logs, telemetry) that do not require joins, PostgreSQL's WAL overhead and autovacuum tuning consume engineering hours; MongoDB's defaults handle similar loads with less friction.

weakness: Insert rates exceeding a few hundred per second [unverified] on modest instances trigger PostgreSQL's autovacuum and connection-pool contention, requiring careful tuning (shared_buffers, work_mem, wal_buffers). A 4-person team without prior PostgreSQL production experience must spend cycles on configuration; MongoDB's defaults scale with less overhead. However, most SaaS MVPs are not write-heavy analytics engines at launch; they're transactional (CRM, project management, e-commerce) with modest write rates (10–100 inserts/sec). The condition holds only for event-driven or analytics-first products, which are a minority of MVPs.

evidence: PostgreSQL's full-row logging does trigger CPU spikes under sustained high-write load [unverified]. MongoDB's document writes do not carry equivalent overhead. Modern PostgreSQL configurations (pgbouncer, tuned autovacuum) mitigate this, but require knowledge. Analyst B's falsification (48-hour load test comparing latency + tuning time) is reasonable but not provided; the claim lacks concrete measurement.

falsification: Run a 48-hour write-heavy load test (5k–10k events/sec) on identically sized instances (e.g., AWS t3.large). Compare (a) sustained insert latency (p50, p99), (b) CPU/memory, (c) tuning hours required. If PostgreSQL latency remains within 10% of MongoDB with minimal configuration, this condition does not fire.

verdict: **MEDIUM, MEDIUM.** Valid for event-heavy or analytics-first products but overly specific; most MVPs do not exhibit this pattern at launch.

**Unplanned horizontal scaling (multi-region replication or 10x write throughput)**

steelman: If the MVP must scale to 2+ regions or 10x write throughput unexpectedly (viral adoption, new customer requirement), MongoDB's native replica sets and sharding are operationally simpler to deploy than PostgreSQL's options (Citus license + learning curve, or application-level sharding).

weakness: By month 5, the team discovers they need multi-region replication or horizontal write-scaling that was not architected at launch. PostgreSQL's path requires either Citus (third-party, licensing, learning curve, ~$500–2000/mo [unverified]) or application-level sharding (complex, error-prone). MongoDB's path: enable sharding on the collection, choose a shard key, done. For a 4-person team, PostgreSQL's path is 3–5 weeks of DevOps; MongoDB's is a configuration change. However, the condition assumes scaling is *unplanned* and urgent—if foreseeable, both architectures should account for it from day 1. Many MVPs do not hit hockey-stick growth within 6 months; the condition fires only when growth is both rapid and unexpected.

evidence: PostgreSQL's logical replication is read-only; write-scaling requires Citus or sharding. Citus has operational and licensing overhead. MongoDB's sharding is built-in and documented. The cost asymmetry is plausible but no concrete DevOps-hours or infrastructure-cost comparison is provided.

falsification: Define unplanned scaling as a requirement to support 10x write throughput on identical infrastructure in < 2 weeks. Measure (a) calendar time from requirement to production-ready, (b) engineer-hours, (c) total cost (infrastructure + licensing). If PostgreSQL time + cost exceeds MongoDB's by > 50%, this condition fires.

verdict: **MEDIUM, MEDIUM.** Realistic scenario for growth-hit-fast startups but narrow condition; fires only if scaling is urgent and truly unplanned within the 6-month window.

**JavaScript-first development team with zero SQL expertise**

target: Analyst B

steelman: When the team's primary language is JavaScript and the 6-month deadline leaves no calendar time to learn GIN indexes, JSONB query planning, or migration frameworks, the cognitive overhead of PostgreSQL exceeds that of a native document store whose drivers map 1:1 with JavaScript objects.

weakness: Analyst B claims developers must master "GIN indexes, JSONB query planning, migration frameworks." This overstates the actual learning curve: modern JavaScript ORMs (Sequelize, TypeORM, Prisma) abstract migrations and JSONB queries; developers rarely tune indexes directly. Most JavaScript developers pick up PostgreSQL basics in days of actual use, not weeks. The asymmetry in learning cost is marginal when both databases are accessed through a mature ORM. The condition holds only if the team has *zero* SQL exposure, refuses ORMs, and must hand-write queries—a rare scenario for professional development.

evidence: Analyst B's falsification (track "DB-related learning hours in first 8 weeks") is difficult to measure because most learning happens incidentally during debugging, not as dedicated study. No concrete measurement is provided. In practice, JavaScript teams using Prisma encounter PostgreSQL and MongoDB APIs simultaneously via the ORM; the difference in setup and query syntax is minimal. The claim about "1.5× MongoDB learning overhead" [unverified] is speculative. Prisma's query builder abstracts both databases to nearly identical JavaScript APIs.

falsification: Measure total engineering hours spent on database-related tasks (schema design, migrations, query debugging, index tuning) during the first 8 weeks for a JavaScript team using a mature ORM (Prisma, TypeORM). If PostgreSQL requires ≤ 1.2× the time of MongoDB, this condition does not materially fire.

verdict: **LOW, LOW-MEDIUM.** Weak evidence; modern ORMs have narrowed the gap. Fires only for teams with zero SQL exposure and no ORM abstraction, which is rare among professional teams.

---

PostgreSQL as the default is acceptable if all four hold: (1) schema stabilizes by month 2; (2) product will require or is architected to avoid cross-entity operations; (3) data is not deeply nested OR team has JSONB expertise; (4) scaling is either planned upfront or not anticipated within 12 months. If any fails AND the product is event-driven or analytics-first, MongoDB becomes safer.
