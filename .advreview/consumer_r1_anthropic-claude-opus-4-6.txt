## Finding 1: Inherently Polymorphic Data Models Make PostgreSQL a Tax on Every Feature

**steelman:** PostgreSQL handles any data shape because JSONB provides schema-free storage within a relational container; the team can mix relational columns for indexed fields with JSONB for the rest.

**weakness:** If the SaaS product's *core entity* is inherently polymorphic — user-defined forms, CMS with arbitrary content types, product catalogs with variable attributes, integration platforms storing third-party payloads — the JSONB escape hatch becomes the *primary* storage pattern, not a supplement. At that point, the team inherits a dual-schema burden: a rigid table-level schema (requiring migrations for structural changes) *plus* an application-level implicit schema inside JSONB (requiring manual validation, explicit type casting for comparisons, and workarounds for GIN index limitations). The Yuriy Ivon analysis identifies concrete costs: JSONB requires explicit casting for non-string fields in queries, GIN indexes do not speed up ordering and perform poorly with `IN`-operator semantics, and PostgreSQL's MVCC model copies the *entire row* on any update — meaning a partial update to one nested field in a large JSONB document rewrites the whole row. MongoDB's BSON partial-update mechanism avoids this. Benchmarks from Binary Igor show PostgreSQL's total table+index size is 2.23× larger than MongoDB for the same 3.4M-record document collection, and MongoDB achieves 4.14× higher throughput on sorted paginated reads of documents. If >60% of the team's queries target variable-structure documents rather than relational joins, PostgreSQL forces the team to pay relational overhead for capabilities they aren't using.

**evidence:** The Medium analysis by Yuriy Ivon confirms JSONB stores field names in every row, requires explicit casting for non-string comparisons, and GIN indexes don't support ordering or `IN`/`LIKE` operators. Binary Igor's benchmark confirms 2.23× storage overhead and 4.14× throughput disadvantage on sorted document reads. The MongoDB engineering blog's update-heavy benchmark (256 concurrent users, 13M documents, 30 minutes) found PostgreSQL's throughput gradually declined and CPU reached saturation while MongoDB remained steady — though no absolute numbers were published, making the magnitude unverifiable.

**falsification:** Profile the actual MVP data model: if >50% of core entities have fixed, known schemas at design time (e.g., users, subscriptions, invoices), the JSONB path is a supplement and this finding doesn't fire. A simple test: can you draw an ER diagram of the core domain with stable column sets for the top 5 entities? If yes, keep Postgres.

**verdict:** high severity · MEDIUM confidence (fires only when the core domain is genuinely polymorphic; many SaaS products have fixed-schema cores)

## Finding 2: Schema Churn During Discovery Phase Creates Compounding Migration Friction

**steelman:** Modern migration tools (Alembic, Flyway) make schema changes cheap — they're just SQL files. Adding a nullable column to PostgreSQL is nearly instant and doesn't rewrite the table.

**weakness:** The cheap operations (add nullable column, add index concurrently) cover only *additive* changes. An MVP in the discovery phase doesn't just add columns — it renames entities, splits tables, changes column types, and drops-then-recreates relationships as the product pivots. Column type changes on populated tables require `ACCESS EXCLUSIVE` locks that block all reads and writes, and on any non-trivial table this can cause application downtime. The Xata/pgroll analysis confirms that when an `ALTER TABLE` waits for a long-running query to release its lock, all subsequent `SELECT` and `UPDATE` statements queue behind it, cascading into an outage. A 4-person team without a DBA is unlikely to implement `lock_timeout` + retry patterns, ghost-table migrations, or `CREATE INDEX CONCURRENTLY` correctly the first time. In MongoDB, renaming a field or changing its type is an application-level concern — you can run old and new shapes side-by-side without any DDL lock, and the migration is a background script that doesn't block reads or writes.

The frequency matters: if the team is iterating weekly on entity shapes (plausible given search results indicating SaaS MVPs cover ~20% of envisioned functionality and iterate aggressively), each non-trivial migration carries risk and consumes engineer-hours on a 4-person team where every hour counts against the 6-month clock.

**evidence:** The Xata engineering blog confirms `ALTER TABLE` acquires `ACCESS EXCLUSIVE` locks and that subsequent reads/writes queue behind blocked DDL. The Bytebase guide on Postgres migration without downtime identifies schema migrations as the most common cause of self-inflicted PostgreSQL downtime. Migration tooling guides confirm that while additive changes are trivial, type changes and table restructuring remain operationally risky.

**falsification:** If the team commits to a disciplined approach — additive-only migrations (new nullable columns, never rename/retype in-place), dual-write patterns for breaking changes, and mandatory `lock_timeout` — Postgres migration costs stay low. Also: if the team uses a managed platform that handles online DDL (e.g., PlanetScale-style for Postgres, though none currently match that level of automation), the risk drops.

**verdict:** medium severity · MEDIUM confidence (depends on actual churn rate; disciplined teams can mitigate, but "disciplined" is a strong assumption for a 4-person startup in discovery mode)

## Finding 3: Zero-Ops Assumption — A 4-Person Team Without a DBA Hits PostgreSQL's Operational Cliff Earlier

**steelman:** Managed PostgreSQL services (Supabase, Neon, AWS RDS) reduce operational burden to near-zero, matching MongoDB Atlas.

**weakness:** Managed services abstract provisioning and backups, but they do *not* abstract the PostgreSQL-specific operational knowledge required when things go wrong: connection pool exhaustion (PostgreSQL's process-per-connection model under concurrent load), vacuum tuning to prevent transaction ID wraparound, index bloat from frequent updates, and the locking behaviors described above. MongoDB Atlas serverless genuinely auto-scales compute and storage with no connection-pool management (the driver multiplexes), and sharding is built into the platform rather than bolted on. For a 4-person team where nobody is a Postgres specialist, the first production incident involving `idle in transaction` connections filling the pool, or autovacuum failing to keep up, or a migration locking a hot table, is a multi-day fire drill that directly threatens the launch timeline. Atlas's operational model is simpler *specifically for the scenario where nobody on the team has deep database expertise*.

**evidence:** The Movestax comparison of serverless databases notes PostgreSQL scales vertically first and requires more operational effort for horizontal scaling. MongoDB Atlas serverless auto-scales resources to match workload demands. The process-per-connection model and vacuum management are well-documented PostgreSQL operational concerns [unverified for specific incident frequency on small teams — reasoning from known architecture]. Managed PG services like Supabase do offer connection pooling via PgBouncer, partially mitigating this.

**falsification:** If at least one team member has shipped a production PostgreSQL application before and is familiar with connection pooling, vacuum tuning, and safe migration patterns, this finding is largely neutralized. Also: if the SaaS is low-concurrency (< 100 concurrent connections), the connection model is a non-issue.

**verdict:** medium severity · LOW confidence (managed services have substantially closed this gap; fires mainly when the team has *zero* Postgres production experience AND faces non-trivial concurrency)

## Finding 4: Write-Heavy Workloads With Large Documents Expose MVCC's Full-Row-Copy Penalty

**steelman:** Most SaaS MVPs are read-heavy; write performance differences are immaterial at MVP scale.

**weakness:** If the SaaS product involves write-heavy patterns on large documents — real-time collaboration (updating sub-fields of a document), IoT/telemetry ingestion, event sourcing with mutable aggregates, or user activity tracking embedded in profile documents — PostgreSQL's MVCC model forces a full-row copy on every update, even if only one nested JSONB field changed. MongoDB's partial-update mechanism (`$set` on a nested path) modifies only the affected bytes. The MongoDB engineering blog's benchmark found PostgreSQL's update throughput gradually declined under sustained write pressure at 256 concurrent users while MongoDB remained steady. Binary Igor's benchmark found MongoDB achieves 42% higher throughput on batch inserts. For a product whose core loop is high-frequency document mutations, this architectural penalty compounds: more dead tuples → more aggressive vacuuming → more I/O → more latency.

**evidence:** The Yuriy Ivon Medium article confirms PostgreSQL's MVCC creates a new row version on every update rather than modifying in place, vs. MongoDB's partial document updates. MongoDB's own benchmark (acknowledged as synthetic) shows PostgreSQL CPU saturation and throughput decline under sustained update workload. Binary Igor's benchmark: 42% batch-insert advantage for MongoDB (115 vs 81 QPS for 1,000-record batches).

**falsification:** If the application's write pattern is predominantly insert-append (logs, events) rather than update-in-place on existing documents, PostgreSQL's append-only MVCC is actually *well-suited*. Also: if documents are small (<4KB), the full-row-copy cost is negligible. Measure the expected update-to-read ratio on core entities; if < 1:5, this doesn't bite.

**verdict:** medium severity · LOW confidence (most SaaS MVPs are not write-heavy on large documents; this is a real but narrow failure mode)

## Finding 5: The "PostgreSQL Can Do Everything" Mindset Delays Acknowledging a Data-Model Mismatch

**steelman:** PostgreSQL's breadth (relational + JSONB + full-text search + vector) means you never need a second database, reducing operational surface area.

**weakness:** This is a cognitive trap specific to the decision framing. Because PostgreSQL *can* handle documents via JSONB, the team may never confront the question of whether it *should*. They'll reach for JSONB workarounds — explicit type casts, custom GIN index expressions, application-level schema validation — instead of recognizing that their data model is fundamentally document-oriented. Each workaround is individually small but collectively they create a codebase full of PostgreSQL-specific JSON manipulation that a MongoDB driver would handle natively. By the time the team realizes the mismatch (typically when query complexity or performance hits a wall), they're 3-4 months into the 6-month timeline and a database migration is off the table. The sunk-cost fallacy kicks in, and they ship an MVP built on the wrong abstraction. MongoDB chosen up front for a document-native workload would have eliminated the entire class of JSONB-related workarounds.

**evidence:** This is a reasoning-chain finding based on the documented JSONB limitations (dual-schema management, casting overhead, GIN gaps). The Yuriy Ivon analysis explicitly notes the burden of maintaining two levels of schema when using JSONB as a primary storage pattern. [unverified for specific team behavioral data — based on architectural reasoning about decision inertia.]

**falsification:** If the team conducts a 1-week data modeling spike before committing — sketching the top 10 queries, the entity shapes, and the expected variability — and finds that >70% of data fits naturally into normalized tables, this cognitive trap doesn't fire because they genuinely have a relational workload.

**verdict:** low severity · LOW confidence (meta-cognitive risk; hard to quantify but real for teams that don't do upfront data modeling)

---

**Acceptability condition:** The PostgreSQL default is acceptable if *all* of the following hold: (1) the core domain entities have stable, known schemas at design time (you can draw an ER diagram with fixed columns for the top 5 entities); (2) at least one team member has production PostgreSQL experience including safe migration practices; (3) the primary access pattern is relational (joins, transactions, aggregations) rather than document-lookup or nested-document-mutation; and (4) the team commits to a managed PostgreSQL service with connection pooling included. If any one of these fails, the team should run a 2-day spike comparing both databases against their actual top-10 queries before committing.
