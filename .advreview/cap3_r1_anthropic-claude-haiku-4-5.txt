## Finding 1: High Schema Churn During Requirements Iteration

**Steelman**: PostgreSQL's schema-first design enforces data integrity from day one, preventing downstream tech debt from inconsistent data shapes even if requirements shift.

**Weakness**: If product requirements evolve significantly during the 6-month MVP cycle—a common pattern in seed-stage SaaS facing market feedback—PostgreSQL imposes a cumulative overhead:
- Each schema change requires: ALTER TABLE operations, migration testing, staged rollouts with rollback plans, and post-migration validation
- Even with managed PostgreSQL (RDS), migrations take 4-8 hours per change (write script, test, monitor lock times, validate), consuming ~2-5% of a 4-person team's capacity
- If the team executes 5 major pivots (user ownership, access control, entity relationships, normalization reversals), that's 20-40 hours of "meta-work" that doesn't ship features

MongoDB's schemaless model allows the same logical pivot to be a pure application change (add field, ignore old one) deployed in <1 hour with zero downtime or coordination overhead. This matters because at MVP stage, constraints are discovered post-launch, not pre-planned.

This weakness **evaporates** if: (a) product definition locks by end of month 1 and schema changes drop to ≤1 per quarter, OR (b) the team has prior Postgres DBA experience and executes migrations in <1 hour consistently, OR (c) the team accepts technical debt (orphaned columns, denormalization) rather than normalize.

**Evidence**: PostgreSQL's schema is enforced by the database engine itself—migrations are transactional operations that require table locks (or slow concurrent rewrites for large tables). MongoDB has no schema enforcement; migrations are application-level code changes with no database-layer tooling overhead.

**Falsification**: In a real product iteration, execute a data-model change on both platforms (e.g., single `user_role` string → `roles` array with metadata). Measure: time from "decision" to "all code using new shape" to "old rows cleaned up." If PostgreSQL consistently completes in ≤2 hours per change and the team successfully rolls back at least once without incident, this finding should be downgraded.

**Verdict**: HIGH severity, MEDIUM confidence. Only applies if schema churn is non-trivial (≥3 changes in 6 months) AND the team lacks migration expertise. Confidence is medium because product volatility is case-dependent and not given in the proposal.

## Finding 2: Operational Readiness and Time-to-Production-Confidence

**Steelman**: PostgreSQL's setup overhead is a one-time investment that prevents costly outages later; early rigor in backup/monitoring/pooling strategy prevents firefighting during peak growth.

**Weakness**: Reaching production-ready PostgreSQL without dedicated ops expertise requires pre-launch operational configuration that consumes weeks of a 4-person team:
- Connection pooling tuning (misconfiguration → connection exhaustion or memory bloat): 4-8 hours [estimated]
- Backup strategy testing (base backup + WAL archiving must be validated; untested backups are useless): 6-12 hours [estimated]
- Monitoring/alerting (slow query logs, table bloat detection, replication lag): 4-6 hours [estimated]
- AUTOVACUUM/parameter tuning for early production workloads: 4-8 hours [estimated]

This totals 18-34 hours [estimated] of non-shipping work before real load hits. Even with RDS (managed service), parameter groups still require post-creation tuning for SaaS workloads that RDS defaults don't assume [unverified specifics].

MongoDB Atlas (the managed service) ships production-ready: automated backups, replica sets enabled by default, monitoring dashboards pre-configured, no DBA-level tuning needed. A team can deploy a production cluster in <1 hour and ship, not operate.

This weakness **evaporates** if: (a) team has a dedicated DevOps/DBA person whose time is already allocated, OR (b) team uses a fully managed PostgreSQL service (not just RDS) that abstracts pooling and parameter tuning, OR (c) operational correctness is non-negotiable (fintech, healthcare) and the team is willing to burn these hours.

**Evidence**: RDS and Atlas differ fundamentally in their assumptions: RDS is a "control plane for Postgres operations" requiring informed configuration choices (connection limits, backup windows, storage scaling triggers); Atlas is a "managed SaaS database" with defaults tuned for typical growth patterns. RDS documentation itself recommends adjusting parameter groups post-creation; Atlas documentation does not.

**Falsification**: Provision both RDS and Atlas via infrastructure-as-code (Terraform), starting from zero configuration. Measure: time to reach a state where (a) backups are tested and restorable, (b) monitoring alerts fire correctly, (c) connection pooling doesn't bottleneck, (d) team can scale without manual intervention. If RDS reaches parity with Atlas in ≤4 hours total and team reports operational confidence, downgrade this finding.

**Verdict**: MEDIUM severity, MEDIUM confidence. Bites hard if team has no ops background AND doesn't use a fully managed service AND wants launch velocity. Confidence is medium because managed Postgres offerings vary.

## Finding 3: Asynchronous Data-Shape Evolution During Feature Rollout

**Steelman**: PostgreSQL's transactional migrations ensure all data is atomically updated; this prevents the subtle consistency bugs of partial rollouts, which are catastrophic in a small team lacking QA resources.

**Weakness**: If the MVP launches and month 3-5 introduces a backward-incompatible data change (e.g., single `user.permissions` field → nested `user.roles[{name, scope}]` array), PostgreSQL requires a coordinated, multi-phase deployment:
1. Deploy new code with dual-read logic (read from both old and new schema)
2. Run migration script (UPDATE users SET roles = …), which either locks the table or runs slowly over days
3. Ensure all replicas have completed the migration before removing dual-read code
4. Deploy code that reads only new schema

This is a 3-7 day choreography window where a single mistake (old code writing, new code not reading old schema, or incomplete migration) forces rollback and re-migration. With a 4-person team, one person is blocked on migration coordination instead of shipping features.

MongoDB allows asynchronous migration: deploy new code that writes V2 and reads both, then background-rewrite old documents lazily (or never, if dual-read remains). Zero downtime, zero coordination risk, zero rollback complexity.

This weakness **evaporates** if: (a) the change is in a critical domain (payments, account balance) where atomicity is a hard requirement and downtime is acceptable to stakeholders, OR (b) data volume is small (<5M rows) and planned downtime is acceptable, OR (c) the application architecture already has feature flags and versioned APIs that make dual-write logic inevitable anyway.

**Evidence**: PostgreSQL enforces schema at the database layer; schema changes are transactional but blocking by design. MongoDB has no schema enforcement; migrations are application-driven and can run asynchronously. This is a fundamental architectural difference.

**Falsification**: Implement a realistic schema pivot (single field → nested array/document) on both platforms with 1-5M existing records [estimated volume for 6-month MVP]. Measure: wall-clock time from "deploy new code" to "100% of reads use new shape" to "100% of old-schema data backfilled" while concurrently measuring whether users see downtime. If PostgreSQL achieves zero-downtime migration in ≤6 hours and team executes it without rollback, downgrade this finding.

**Verdict**: MEDIUM severity, MEDIUM confidence. Only bites if (a) changes are non-critical-path (not payments), (b) team is risk-averse about coordinated deploys, (c) downtime is unacceptable. If the feature is in a domain where atomicity is critical, PostgreSQL's design is actually safer.

## Meta-Finding: Flawed Premise in the Proposal

The proposal assumes PostgreSQL is universally worse for a 4-person MVP. This inverts a false binary: neither database is objectively better—the tradeoff is **multi-dimensional**:

- **PostgreSQL excels at**: schema integrity, complex queries, ACID atomicity, regulatory compliance
- **MongoDB excels at**: schema flexibility, operational simplicity (with managed Atlas), rapid iteration, asynchronous data migration

The true vulnerability is that the proposal omits:
- How volatile are feature requirements? (churn → MongoDB wins; stable → PostgreSQL wins)
- How critical is atomicity? (payments/audit → PostgreSQL wins; engagement features → MongoDB wins)
- Does the team have ops expertise? (yes → PostgreSQL overhead acceptable; no → MongoDB wins)
- What is the customer tolerance for downtime during migrations? (zero tolerance → MongoDB wins; accepting → PostgreSQL acceptable)

Without these inputs, claiming one is "worse overall" is premature. The correct choice requires specifying risk tolerance and feature domain.

---

**PostgreSQL becomes acceptable when ALL of the following hold:**
1. Feature set is data-integrity-critical (payments, regulatory audit, account balance) AND downtime for migrations is acceptable to stakeholders.
2. Team has or will hire DevOps/database expertise within the first 2 months, OR commits to a fully managed Postgres service and accepts 2-4 hours [estimated] of tuning overhead.
3. Product requirements are locked by end of sprint 1 and schema pivots are ≤1 per quarter thereafter.

**Otherwise, MongoDB (with managed Atlas) is likely superior for the stated constraints.**
