## Finding 1: Inherently Polymorphic or Tenant-Variable Data Makes PostgreSQL the Wrong Abstraction

**target:** Analyst B (Finding 3), reinforcing and merging with my prior Finding 1

**steelman:** PostgreSQL handles variable-structure data via JSONB, so the team never needs a second database. Even per-tenant custom fields or integration payloads can live in a JSONB column while the stable core stays relational. Analyst B is right that this failure mode exists, but the HIGH confidence assigned assumes it fires frequently for SaaS MVPs.

**weakness:** When schema heterogeneity is a *first-class product feature* — customer-defined fields, integration-specific payloads that must be queried and filtered, versioned objects with materially different field sets, or multi-tenant configuration that varies by customer — PostgreSQL's JSONB escape hatch becomes the primary storage pattern, not a supplement. The PostgreSQL JSON documentation itself warns that documents should still have "a somewhat fixed structure" and that "any update acquires a row-level lock on the whole row." MongoDB's schema validation explicitly distinguishes required fields from optional ones and enforces rules only when a field exists (verified: the validation example checks `gpa` only "if the field exists"), giving the team a native way to validate the stable core while leaving the variable envelope unconstrained. In PostgreSQL, the team must either (a) add relational migrations for every new variant (unsustainable), or (b) shift variance into JSONB and lose the schema stability that justified choosing Postgres — carrying both relational and document-model complexity in one system. The JSONB path imposes additional costs: field names are stored in every row (no shared schema dictionary), non-string comparisons require explicit casting, and GIN indexes don't support ordering or range queries on nested fields.

**evidence:** PostgreSQL JSON docs (verified): "any update acquires a row-level lock on the whole row" and documents should have "a somewhat fixed structure." MongoDB validation docs (verified): `gpa` is validated only "if the field exists," demonstrating optional-field enforcement. The Yuriy Ivon analysis confirms JSONB stores field names per-row, requires explicit casting, and GIN indexes don't support ordering. Binary Igor's benchmark confirms 2.23× storage overhead for JSONB vs BSON on 3.4M records.

**falsification:** Inventory every planned source of schema variation. If the non-uniform fields are small, non-queryable blobs (opaque JSON stored and returned whole, never filtered against), PostgreSQL absorbs them without friction. The finding fires only when variable-structure data must be queried, filtered, or indexed.

**verdict:** high severity · MEDIUM confidence (fires when polymorphism is a first-class queryable feature; many SaaS products have fixed-schema cores where this doesn't apply)

## Finding 2: Aggregate-Centric Read/Write Workloads Pay a Structural Tax in PostgreSQL

**target:** Analyst B (Finding 2) — I largely agree with the mechanism but challenge the HIGH confidence rating

**steelman:** When the dominant unit of work is a bounded nested aggregate (workflow definitions, onboarding state, template documents, tenant configurations) that is fetched whole and written whole, MongoDB's document model is the natural storage primitive. PostgreSQL forces an awkward choice: normalize and pay in joins and multi-table writes, or use JSONB and concentrate contention on one row.

**weakness:** This finding holds when the aggregate is genuinely self-contained. MongoDB's single-document atomicity (verified: "A denormalized data model that uses embedded documents and arrays combines all related data in a single document...This data model allows atomic operations") eliminates the multi-table transaction overhead PostgreSQL requires for normalized aggregates. PostgreSQL's own JSON docs confirm row-level locking on any JSONB update, serializing concurrent edits to the same aggregate.

However, Analyst B's HIGH confidence understates two counter-costs that narrow MongoDB's advantage in practice: (1) **Cross-aggregate queries emerge inevitably.** An MVP that starts with "show me this project's tasks" will, within months, need "show me all overdue tasks across all projects." MongoDB's `$lookup` for cross-collection queries lacks hash joins and merge joins. A MongoDB community thread discussing whether `$lookup` is "still 130 times worse than Postgres" went unrefuted from 2022 through 2024. MongoDB's own developer advocate benchmarked `$lookup` at 10 seconds for 1 million documents and concluded that `$lookup` is "not designed to join scalar values from thousands of documents," recommending denormalization instead. (2) **MongoDB's 16 MiB document size limit** (verified) means aggregates that grow over time (projects accumulating thousands of tasks, comments, events) must eventually be extracted into separate collections — reimplementing the relational model inside MongoDB.

**evidence:** MongoDB docs (verified): single-document writes are atomic; denormalized embedded documents "continue to be optimal for your data and use cases" in most scenarios. But MongoDB's own best practices recommend references over embedding when "the child side of the relationship has high cardinality" or "your embedded data grows without bounds" (verified). MongoDB's document size limit is 16 mebibytes (verified). The `$lookup` benchmark from MongoDB's own DEV Community article shows 10-second latency on 1M documents with IndexedLoopJoin. PostgreSQL JSON docs (verified): "any update acquires a row-level lock on the whole row."

**falsification:** Sample the top 20 reads and writes. If >70% are aggregate-scoped (no cross-aggregate joins, no sub-part filtering across aggregates) and aggregates remain bounded (< 1,000 embedded items), this finding holds. If >30% of queries need cross-entity filtering within 6 months, MongoDB's advantage erodes and `$lookup`'s poor join performance becomes the bottleneck instead.

**verdict:** high severity · MEDIUM confidence (mechanism is sound but HIGH confidence is unjustified because cross-aggregate queries and unbounded growth are likely to emerge during the MVP lifecycle)

## Finding 3: Non-Additive Schema Changes on Hot Tables Are the Real Hazard — But Both Analysts Overstate Its Severity at MVP Scale

**target:** Analyst A (Finding 1, round 2), Analyst B (Finding 1)

**steelman (Analyst A):** Even with additive discipline, the first production pivot requiring a type change or NOT NULL on an existing column acquires ACCESS EXCLUSIVE. The team has no buffer to implement shadow-table patterns under load, and the resulting lock queue blocks every SELECT for the duration of the table rewrite.

**steelman (Analyst B):** PostgreSQL is the wrong default when core product objects are still being discovered in production and require repeated live changes to required fields, field types, or nullability on high-traffic tables.

**weakness:** Both analysts correctly cite the ACCESS EXCLUSIVE lock mechanism (verified: "An ACCESS EXCLUSIVE lock is acquired unless explicitly noted") and the table-scan requirement for SET NOT NULL (verified: "ordinarily this is checked during the ALTER TABLE by scanning the entire table"). The Xata blog confirms the cascading lock queue: "Any other statements that require a lock on the users table are now queued behind this ALTER TABLE statement."

However, both assign critical severity without accounting for three scale-dependent mitigations:

1. **Table size at MVP scale.** A column type change rewrites the table (verified: "Changing the type of an existing column will normally cause the entire table and its indexes to be rewritten"). But rewrite time is proportional to table size. At 100K rows, a rewrite completes in under a second. The ACCESS EXCLUSIVE lock is held for that duration — sub-second. The cascading lock queue only causes meaningful downtime when the rewrite takes minutes (millions of rows) or when a long-running query is already blocking the DDL.

2. **PostgreSQL 18 (released September 2025) introduces NOT NULL NOT VALID.** Verified via Neon's documentation: this allows adding NOT NULL constraints without scanning existing data, using only a "brief ACCESS EXCLUSIVE lock," with subsequent validation using a "SHARE UPDATE EXCLUSIVE lock" that "allows reads and writes during validation." This eliminates the SET NOT NULL table-scan hazard that both analysts cite as a key risk. Since the team is building now (June 2026), PostgreSQL 18 is available.

3. **The lock_timeout pattern is trivial.** The Xata blog prescribes it in one line: `SET lock_timeout = '2s'`. This prevents the cascading queue entirely. A 4-person team can learn this in 30 minutes.

The critical severity assigned by both analysts is only justified if the team (a) has tables with millions of rows, (b) needs frequent type changes (not just additive columns), (c) is on PostgreSQL < 18, AND (d) doesn't set `lock_timeout`. At MVP scale in 2026, the conjunction of all four is unlikely.

**evidence:** PostgreSQL ALTER TABLE docs (verified): ACCESS EXCLUSIVE lock acquired by default; column type changes rewrite the table; adding nullable columns does NOT rewrite. PostgreSQL 18 NOT NULL NOT VALID feature (verified via Neon): adds constraint without table scan, validation step uses SHARE UPDATE EXCLUSIVE lock allowing concurrent reads and writes. Xata blog (verified): cascading lock queue occurs when DDL is blocked behind a long-running query; solution is `SET lock_timeout`.

**falsification:** If the team expects >5M rows in a core table within the first 3 months AND plans non-additive DDL (type changes, restructuring) on that table during production traffic, the critical rating holds regardless of PostgreSQL version. Track the first 8 weeks: if >30% of migrations are non-additive, upgrade this to high severity.

**verdict:** medium severity · MEDIUM confidence (mechanism is real and verified, but critical/HIGH ratings from both peers overstate the impact at MVP scale on PostgreSQL 18; the most dangerous sub-case — SET NOT NULL — is now mitigated by NOT VALID syntax)

## Finding 4: Write-Heavy Large-Document Updates Expose MVCC's Full-Row-Copy Penalty

**steelman:** Most SaaS MVPs are read-heavy; write performance differences are immaterial at MVP scale.

**weakness:** If the SaaS product's core loop involves frequent partial updates to large JSONB documents — real-time collaboration, activity feed updates embedded in user profiles, feature flag state mutated per-request — PostgreSQL's MVCC model copies the entire row on every update, even when only one nested field changed. PostgreSQL's own docs confirm: "any update acquires a row-level lock on the whole row." MongoDB's `$set` operator modifies only the targeted path within the BSON document. Under sustained update pressure, PostgreSQL accumulates dead tuples that autovacuum must clean, while MongoDB's in-place partial updates avoid this overhead entirely. However, this failure mode is narrow: it requires large documents (>4KB), high update frequency on the same documents, and partial-update patterns (not whole-document replacement).

**evidence:** PostgreSQL JSON docs (verified): "any update acquires a row-level lock on the whole row." MVCC full-row-copy behavior is architectural. MongoDB's partial-update mechanism is well-documented. Binary Igor's benchmark shows 42% batch-insert advantage for MongoDB (115 vs 81 QPS for 1,000-record batches). MongoDB's own benchmark (acknowledged as synthetic) showed PostgreSQL CPU saturation under sustained update workload.

**falsification:** If documents are small (<4KB) or the update pattern is insert-append rather than update-in-place, the row-copy cost is negligible. Measure the expected update-to-read ratio on core entities; if < 1:5 and average document size < 4KB, this finding doesn't fire.

**verdict:** medium severity · LOW confidence (narrow failure mode; most SaaS MVPs are not write-heavy on large documents)
