## 1. High Frequency Schema Changes Necessitate Continuous Migrations

**Steelman**: PostgreSQL's schema-on-write enforcement prevents silent data corruption and forces disciplined design upfront, which a focused team can achieve even in 6 months.

**Weakness**: If the MVP's data model emerges through hypothesis-driven iteration (e.g., pivoting between user personas, discovering unexpected relationships), the team will face 5+ schema revisions. Each revision in PostgreSQL requires an ALTER TABLE migration script, testing in a staging environment, and a deployment that blocks other changes. A 4-person team loses weeks cumulatively to this gating, especially if they lack automated migration infrastructure (e.g., no Alembic + CI/CD pipeline). MongoDB's schema-less approach allows additive changes (new fields in documents) without downtime or coordination, letting the team ship and iterate without a migration bottleneck.

**Evidence**: PostgreSQL migrations are sequential; running `ALTER TABLE` on a live table under load risks lockouts or replication lag. Testing each migration requires a production-shaped environment. Revising schema after launch (common in MVP pivots) triggers coordination overhead. MongoDB's aggregation pipeline and dynamic field indexing sidestep this friction—the application code simply adds fields to documents as needed. The hidden premise is that schema is knowable at launch; hypothesis-driven MVPs violate this.

**Falsification**: Audit the product spec for locked requirements. If the core data relationships are stable (e.g., SaaS for a well-understood domain with competitor analysis), or if the team already has zero-downtime migration tooling deployed, this risk vanishes. Inspect git history for schema change frequency; if <2 schema revisions expected, premise holds.

**Verdict**: **High** severity, **MEDIUM** confidence.  
High severity: schema churn directly delays launch or forces hacky workarounds. MEDIUM confidence: depends on actual requirement volatility, which is not specified.

## 2. Unexpectedly Rapid Growth Triggers Horizontal Scaling Mid-MVP

**Steelman**: PostgreSQL's read-replica architecture and mature ecosystem (pgBouncer, connection pooling) are proven at scale and more operationally transparent than MongoDB's eventual-consistency tradeoffs.

**Weakness**: If the MVP gains product-market fit earlier than expected (e.g., month 4-5, before planned post-launch optimization), single-node PostgreSQL hits saturation in storage or query throughput. Horizontal scaling PostgreSQL requires:
- **Application-level sharding** (manually splitting tables across instances, maintaining shard keys in code—complex and fragile), OR  
- **Citus** (requires relicensing, re-architecting, and operational expertise a 4-person team doesn't have), OR  
- **Read replicas only** (solves read scaling but not write-scaling bottlenecks).

A 4-person team cannot pause feature development to hire DevOps and rebuild infrastructure mid-MVP. MongoDB's built-in sharding allows the team to add shard servers without code changes, avoiding the forced pivot. The consequence is performance degradation, user churn, or forced abandonment of the MVP to rebuild.

**Evidence**: PostgreSQL write scaling is fundamentally hard; replication is read-only by default. Sharding requires application awareness of shard logic (modulo hashing, shard migration scripts). MongoDB's sharded cluster automatically routes writes and rebalances data via config servers—operationally simpler for small teams. The hidden premise is "scaling is a post-launch concern"; early traction falsifies this.

**Falsification**: Model expected growth: if data volume stays <50GB and QPS <500 within 6 months, single-node PostgreSQL suffices. If the product targets a niche market or B2B segment with predictable adoption, this risk is low. Check go-to-market strategy; if it's slow-burn (not viral), risk is lower.

**Verdict**: **High** severity, **LOW-MEDIUM** confidence.  
High severity: unplanned scaling forces costly re-architecture or loses users. LOW-MEDIUM confidence: the timing and magnitude of traction are unknowable; this only bites under specific market conditions.

## 3. Team Skill Composition Favors Document Models Over Relational Thinking

**Steelman**: SQL and relational modeling are industry-standard; adopting PostgreSQL forces the team to build transferable expertise.

**Weakness**: If the 4-person team has a background in Node.js/Python, document databases, or ORM-heavy frameworks (Rails with associations), but minimal hands-on SQL experience, PostgreSQL development is slower and error-prone. The team must learn:
- Normalization and foreign keys (cognitive overhead),
- JOIN syntax and query optimization (N+1 queries are common in inexperienced hands),
- Transactions and isolation levels (sources of bugs in concurrent scenarios).

MongoDB's document model maps directly to application objects (JSON-like structures), allowing the team to use familiar patterns immediately. For a 4-person team under 6-month pressure, reducing cognitive friction—even at the cost of eventual consistency and weaker guarantees—speeds development. The consequence is slower query writing, more bugs in complex queries, and delayed feature delivery.

**Evidence**: Relational design requires internalizing 3NF trade-offs and understanding JOIN performance; this is non-trivial for developers without SQL production experience. MongoDB aggregation pipelines use declarative syntax similar to functional programming, which is more intuitive to modern developers. The hidden premise is that SQL fluency is "free"; skill gaps are costly under time pressure.

**Falsification**: Conduct a skills audit: ask each team member to write a SQL query with 3+ table joins and optimize it for a 1M-row table. If 3 out of 4 succeed within 15 minutes, the team has sufficient SQL depth; this risk is low. Alternatively, if the team can hire a senior SQL engineer before development starts, this risk evaporates.

**Verdict**: **Medium** severity, **LOW** confidence.  
Medium severity: skill misalignment causes delays but is addressable through hiring or training. LOW confidence: team composition and actual SQL experience are not specified; this is speculative.

---

**Acceptable only if**: All three conditions are ruled out—i.e., schema is locked, growth is predictable and moderate, and team members can demonstrate hands-on PostgreSQL/SQL expertise under time pressure. Otherwise, MongoDB's flexibility and reduced operational burden outweigh PostgreSQL's consistency and tooling advantages for this specific constraint set.
