- steelman: PostgreSQL is still the safer default if schema churn is mostly additive and can be handled with ordinary migrations before tables become hot.
- weakness: PostgreSQL becomes strictly worse than MongoDB when the MVP’s core persisted objects are still changing in non-additive ways after production traffic starts: type changes, later `NOT NULL` enforcement, validated constraints, or columns added with volatile defaults on hot tables. That is the edge case Analyst A was pointing at, but the narrower version survives challenge: not every product experiment is painful, only the class that turns product iteration into lock-sensitive DDL. In that condition, a 4-person team burns launch time choreographing rewrites, scans, and lock windows; MongoDB can usually ship the same iteration as application-level document-shape changes while validating only the stable subset.
- evidence: PostgreSQL states that `ALTER TABLE` acquires an `ACCESS EXCLUSIVE` lock unless noted otherwise, that `SET NOT NULL` ordinarily checks by “scanning the entire table,” and that changing a column type will “normally cause the entire table and its indexes to be rewritten”; it also notes such rebuilds “may take a significant amount of time” and can require “as much as double the disk space.” PostgreSQL also says changing a default “will only apply in subsequent `INSERT` or `UPDATE` commands,” which defeats Analyst B’s broader claim that every experiment implies a backfill or dual-write; the real failure mode is live non-additive change on hot data, not additive evolution in general. MongoDB’s schema-validation example shows required fields can coexist with optional ones, including the verified rule `"'gpa' must be a double if the field exists"`. Mechanism: unstable live schema -> lock/rewrite/scan operations on production tables -> operational work and delay on a fixed 6-month clock -> MongoDB wins by decoupling many shape changes from DDL.

- falsification: Classify the next 10 expected schema changes before launch. If nearly all are new tables, new nullable columns, or defaults that affect only future writes, and none require hot-table rewrites or validation scans, this failure mode weakens sharply.
- verdict: critical | HIGH

- steelman: PostgreSQL can store nested data in `jsonb`, so choosing it does not automatically force full normalization.
- weakness: PostgreSQL is strictly worse when the dominant unit of work is a bounded nested aggregate that the app usually fetches whole and updates whole: onboarding state, workflow definitions, tenant configuration, generated-artifact manifests, or similar. This survives challenge only in the bounded case. MongoDB’s own modeling guidance cuts both ways: embedding is favored when data is queried and updated together, but not when embedded data grows without bounds, has high cardinality, or is written at different times in a write-heavy workload. Under the bounded-aggregate condition, MongoDB stores the natural object directly and gives atomic single-document writes. PostgreSQL forces an awkward choice: normalize and pay with multi-table read/write paths, or keep the aggregate in `jsonb` and serialize independent edits through whole-row locking.
- evidence: MongoDB says “Keeping related data together will lead to a simpler data model and code,” recommends embedding when the application “queries pieces of information together” and when data is “often updated together,” and states that write operations are atomic “on the single-document level.” The same MongoDB page also says to prefer referencing when embedded data has high cardinality, grows without bounds, or is “written at different times in a write-heavy workload,” which narrows the finding and defeats overbroad pro-Mongo versions. PostgreSQL says JSON can be compelling when requirements are fluid, but still recommends a “somewhat fixed structure,” and warns that “any update acquires a row-level lock on the whole row.” Mechanism: aggregate-centric hot path -> MongoDB aligns storage with the app’s native object -> fewer joins and simpler atomicity; PostgreSQL either fragments the aggregate or concentrates contention in one row.

- steelman: A small amount of variable data inside PostgreSQL is not disqualifying; `jsonb` can absorb edge-case flexibility while the core remains relational.
- weakness: PostgreSQL becomes strictly worse when heterogeneity is not an edge case but a first-class MVP requirement: tenant-defined fields, integration-specific payloads that remain queryable, or versioned objects whose field sets materially differ by customer or workflow. This is the surviving version of Analyst B’s flexibility concern. In that case the team either keeps paying relational-migration costs for every newly important variant or shoves the variance into `jsonb` and gives up much of the fixed-schema benefit that justified PostgreSQL in the first place. MongoDB is better because it can enforce the invariant core while leaving the variable envelope optional.
- evidence: MongoDB’s validation example explicitly separates required fields from optional ones, again showing the verified optional rule `"'gpa' must be a double if the field exists"`. PostgreSQL says JSON is useful when “requirements are fluid” but still recommends documents with a “somewhat fixed structure.” Mechanism: intentionally polymorphic core entities -> fixed relational schema stops being the natural contract -> PostgreSQL either incurs repeated schema work or carries a document model inside a relational system -> MongoDB’s default matches the workload better.
