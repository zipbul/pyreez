- steelman: PostgreSQL is the safer default because an MVP usually benefits from SQL, constraints, and predictable structure, and a small team can tolerate some migration work.
- weakness: PostgreSQL is the wrong default if the core product objects are still being discovered in production, not just extended occasionally. If the team expects repeated live changes to required fields, field types, or nullability on high-traffic tables during the 6-month build, Postgres turns those product pivots into operational events: `ALTER TABLE` commonly takes an `ACCESS EXCLUSIVE` lock, some changes trigger full table and index rewrites, and new constraints can require full scans that lock out updates until commit. MongoDB is strictly better in that condition because it allows writes without a predefined schema and supports selective schema validation, so the team can ship evolving document shapes without coupling each learning cycle to DDL risk.
- evidence: PostgreSQL documents that `ALTER TABLE` acquires an `ACCESS EXCLUSIVE` lock unless noted otherwise, that changing a column type will normally rewrite the entire table and its indexes, and that adding `CHECK` or `NOT NULL` constraints requires scanning the table; for large tables, these operations can take significant time and lock out updates. MongoDB states that with relational databases you must define schema before adding data, while its model allows inserting without a predefined schema and making changes without interruption; its validation rules can also omit fields and are most useful only once the structure is established. Mechanism: unstable product model -> repeated DDL on live tables -> lock/rewrite/scan overhead -> 4-person team burns launch time on migration choreography instead of feature work.
- falsification: Write the next 12 weeks of product changes as concrete examples. If at least 90% of persisted fields can be named, typed, and made nullable/non-nullable now, and remaining changes are additive columns without hot-table rewrites, this failure mode weakens sharply and Postgres is safe to keep.
- verdict: critical, HIGH

- steelman: Even if requirements move, PostgreSQL can still hold nested data with `jsonb`, so choosing Postgres does not necessarily force full normalization.
- weakness: PostgreSQL loses when the dominant unit of work is a nested aggregate that the app reads and writes as one thing: for example, a project, workflow, onboarding state, generated artifact, or tenant configuration document with embedded items that are queried together and updated together. In that case MongoDB’s document model is the natural fit, while Postgres forces an awkward choice: normalize and pay in joins and multi-table write paths, or use `jsonb` and keep the document shape inside rows that still lock at the whole-row level on update. For an MVP, that trade is bad if the team’s hot path is mostly aggregate reads/writes and cross-aggregate relational queries are rare.
- evidence: MongoDB’s data-modeling guidance says keeping related data together leads to a simpler model and code, embedding fits when the application queries information together or updates it together, and duplicating data can remove joins and improve read performance. MongoDB also states single-document writes are atomic and that embedded documents and arrays are often the optimal way to avoid costlier distributed transactions. PostgreSQL’s JSON docs say JSON is more flexible when requirements are fluid, but still recommend a somewhat fixed structure, and warn that any update to JSON data acquires a row-level lock on the whole row. Mechanism: aggregate-centric workload -> Mongo can store the aggregate as the primary unit -> simpler read/write path and atomic updates -> Postgres either fragments the aggregate across tables or concentrates contention in one row.
- falsification: Sample the top 20 reads and writes. If most requests need relational joins across independent entities, or independent subparts of the aggregate must be updated concurrently by different actors, Postgres remains reasonable and Mongo’s document advantage narrows.
- verdict: high, HIGH

- steelman: A small amount of flexible data can be parked in JSON in PostgreSQL while the important business entities stay relational.
- weakness: PostgreSQL becomes strictly worse if flexibility is not edge-case metadata but a first-class product feature: per-tenant custom fields, polymorphic records, third-party webhook payloads, or user-authored objects where only some fields are common and the rest vary by customer, integration, or version. MongoDB is better there because it can validate only the stable subset and let the variable remainder evolve without synchronized schema work. Postgres can imitate this with `jsonb`, but then the default decision is no longer buying the main thing it assumed it was buying: a stable relational schema. The team ends up carrying both relational and document-model complexity inside one system.
- evidence: MongoDB explicitly says schema validation rules “don't need to cover every field in a document” and are most useful for an established application with a defined structure. PostgreSQL says JSON can be compelling when requirements are fluid, but recommends that JSON documents still have a somewhat fixed structure. Mechanism: heterogeneous tenant or integration payloads -> stable core plus unstable per-record variation -> Mongo validates the core and ignores the rest -> Postgres either accumulates migrations for every new variation or shifts the variability into JSON and loses much of the simplicity that motivated choosing Postgres.
- falsification: Inventory every planned flexible field source. If custom fields are truly non-queryable blobs, or the variable parts are small and isolated from the MVP’s core entities, Postgres is still acceptable.
- verdict: medium, HIGH

Acceptable only if the MVP’s core entities are already mostly known, live schema changes will be infrequent and mostly additive, and the hot path is not document-centric or tenant-polymorphic.
