---

**Explosive growth exceeding single-instance capacity within 6 months**

**Steelman:** For most MVPs, vertical scaling is sufficient. But if product-market fit is immediate and usage spikes, a single-instance PostgreSQL database becomes a hard ceiling.

**Weakness:** If the MVP grows to high write/read throughput (multi-thousand QPS) or large dataset size before month 6, PostgreSQL's architecture requires sharding. PostgreSQL offers no native sharding: retrofitting it requires application-level shard-key selection, routing logic, managing multiple instances, and handling distributed transaction consistency. MongoDB's Sharded Clusters are transparent at the driver layer and scale linearly by adding nodes. A 4-person team forced into a sharding retrofit mid-MVP is derailed for weeks.

**Evidence:** PostgreSQL's largest single instance (modern cloud hardware) handles ~5-10k concurrent connections but architecture assumes one writer. Sharding requires either external tools (Citus, which adds licensing/ops burden) or application rewrites. MongoDB sharding is a first-class primitive with automatic chunk balancing and shard-key range management built into drivers. Growth 10x in 3 months + single-node bottleneck = PostgreSQL loses badly.

**Falsification:** Deploy both under synthetic load simulating 10x growth in 6 months. Measure time-to-sharding and feature-development disruption. If PostgreSQL handles this growth on one instance, or if sharding retrofit takes <2 weeks with no application-layer changes, the weakness doesn't bite.

**Verdict:** severity: **critical** | confidence: **MEDIUM** — The condition (explosive growth + hitting single-instance ceiling within 6 months) is plausible for viral products but rare for typical B2B MVPs. Consequences are severe only *if* the condition holds.

**Frequent schema evolution (2+ changes per sprint) without a mature migration process**

**Steelman:** PostgreSQL's ACID guarantees and schema rigor are assets for stable systems. But MVPs often have uncertain data models.

**Weakness:** If the team's requirements shift and the schema changes 2+ times per sprint—column renamings, relationship restructuring, type changes—PostgreSQL's explicit migration model creates velocity drag. Each non-trivial schema change requires a migration script, coordination between database and code deploys, and testing. Blocking ALTER TABLE operations risk downtime; zero-downtime patterns (logical replication, online schema change tools) are operationally complex for a team of 4. MongoDB's schemaless model allows developers to add fields, nest structures, and abandon old fields without migration coordination—deploy the code, it works.

**Evidence:** PostgreSQL's ADD COLUMN is O(1) with recent versions, but column renames, type changes, and relationship modifications require explicit DDL scripts and careful coordination. A team iterating rapidly on domain modeling makes these changes frequently. MongoDB validation schemas are optional; default behavior accepts any structure.

**Falsification:** Track actual schema-change frequency in the first 3 months of development. If <1 per sprint, this weakness never applies. If ≥2 per sprint and PostgreSQL migration overhead measurably exceeds MongoDB field-addition time by >2 hours per sprint, weakness is real. If the team adopts zero-downtime migration tooling from day 1 and overhead is negligible, weakness is defeated.

**Verdict:** severity: **high** | confidence: **MEDIUM** — The technical limitation (explicit migrations vs. schemaless) is real and deterministic. Whether the condition applies depends on actual schema volatility during early development. Confidence is MEDIUM because schema evolution depends on domain uncertainty, which is unknown upfront.

---

**Inherently document-oriented application domain (e.g., form builder, CMS, multi-tenant analytics)**

**Steelman:** Some applications naturally benefit from relational normalization and ACID guarantees. Others are fundamentally document-centric.

**Weakness:** If the MVP's core entities are deeply nested and heterogeneous—e.g., Form → Fields → Validators → ErrorMessages, or Customer → Events (heterogeneous event types)—PostgreSQL requires careful normalization across multiple tables. Each query retrieving a Form with all its Fields requires JOINs; ORM impedance mismatch emerges when loading related objects. MongoDB's document model embeds nested arrays and objects directly. A Form is one document; a query fetches it atomically. Schema design overhead is lower; developers iterate faster on core features instead of optimizing JOINs. For a 6-month deadline, this velocity difference is material.

**Evidence:** A "Form" entity in MongoDB is a single document with embedded `fields: [{...validators: [{...}]...}]`. In PostgreSQL, that's forms table + fields table + validators table + JOINs + GROUP_CONCAT aggregation or post-fetch filtering in application code. For rapid prototyping of complex nested structures, MongoDB's model maps directly to developer intuition.

**Falsification:** Build the MVP's core domain model in both databases. Measure time-to-first-working-feature for CRUD operations on the deeply nested entity. If PostgreSQL is equal or faster, or if the application's data model is relational (many-to-many, complex joins), weakness doesn't apply.

**Verdict:** severity: **medium** | confidence: **MEDIUM** — The technical fit (document model vs. relational) is real and measurable. Whether the application is document-oriented is domain-specific and unknown without examining the application's data model. Applies to form builders, headless CMS, customer analytics, and multi-tenant dashboards; doesn't apply to marketplace, booking system, or financial transaction MVP.

---

**No single condition ensures PostgreSQL is worse. The proposal (PostgreSQL as default) is acceptable *if* the team:**  
**(a) expects stable schema by month 2, (b) anticipates <2x data growth in 6 months, or (c) the application is fundamentally relational (many-to-many, normalization-heavy).** It fails if all three are violated: schema is volatile, growth is explosive, and the domain is document-centric.
