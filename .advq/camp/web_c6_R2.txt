## Consolidated Final Stress-Test: React SPA → RSC Migration for Large E-Commerce

### Finding 1 — Bundle-Size Premise Structurally Collapses for Interaction-Heavy Commerce UIs

**target:** the proposal

**steelman:** RSC genuinely eliminates JavaScript for components that render exclusively on the server. A product catalog rendered server-side ships zero component JS to the browser — measurably improving parse time on low-end devices.

**weakness:** Every feature of a large e-commerce site that users interact with — add-to-cart buttons, variant selectors, quantity pickers, Stripe Elements, real-time inventory badges, Algolia instant search, live chat overlays, A/B testing scaffolding — requires browser APIs or event handlers and forces a `"use client"` boundary. When third-party library incompatibilities surface during build (the default for mature SPAs using Material UI, Chakra, Emotion, or styled-components), the natural resolution is placing `"use client"` high on a shared component file. This silently promotes the entire import subtree to client components, erasing every bundle saving while the full RSC architectural complexity cost (server/client boundary reasoning, async component constraints, router cache management) remains. The net outcome is a larger engineering surface area for an unchanged bundle.

**evidence:** "Every component is a Client Component. Every component ships JavaScript to the client. The RSC architecture is in place — the routing, the layout, the page files — but the actual benefit (JavaScript that never ships) is zero." ([LogRocket RSC pitfalls, blog.logrocket.com](https://blog.logrocket.com/react-server-components-performance-mistakes).) Analyst A's Finding 3 on CSS-in-JS confirms the same collapse mechanism from a different entry point, with the Mux 50k-line migration independently calling CSS-in-JS "probably the biggest part of our RSC conversion." These are independent lines of evidence converging on the same failure mode.

**falsification:** Run `@next/bundle-analyzer` on the migrated build. If the client JS bundle is ≥ 90% of the pre-migration baseline, the premise has failed regardless of what the architecture diagram says.

**severity:** critical
**confidence:** HIGH

### Finding 2 — TTFB Regression Evidence Is Anecdotal and Infrastructure-Confounded; HIGH Confidence Is Inflated (Challenge to Analyst A's Finding 1)

**target:** Analyst A

**steelman:** Moving React rendering to an origin server adds per-request CPU cost proportional to component-tree complexity. Under load, without aggressive edge caching, this structurally increases TTFB regardless of implementation quality.

**weakness:** Analyst A cites a single blog post (Krishnajlathi, Medium, April 2026) showing 180ms → 620ms TTFB as HIGH confidence evidence. Three problems: **(a)** The article states the experiment covered "only one route" with React Server Components — this is a controlled experiment on a single path, not a whole-app production result. **(b)** The SPA baseline TTFB of 180ms is itself abnormal: a well-configured CDN-served SPA (S3 + CloudFront, Vercel Edge, Fastly) serves static assets in 20–50ms from edge nodes. A 180ms SPA baseline indicates the SPA was also being served from origin or from a poorly configured CDN, making the comparison origin-server vs. origin-server rather than the relevant CDN vs. RSC comparison. **(c)** No infrastructure context is given: server region count, whether Next.js streaming was enabled, whether the RSC responses had cache headers set. HIGH confidence on a single uncontrolled blog post is an inflation. The mechanism (origin compute per request) is sound and earns MEDIUM confidence; the specific numbers do not.

**evidence:** Medium article confirmed by search (URL: [medium.com/@Krishnajlathi/react-server-components-reduced-js-but-our-ttfb-went-the-wrong-way-d87dd26f8aa5](https://medium.com/@Krishnajlathi/react-server-components-reduced-js-but-our-ttfb-went-the-wrong-way-d87dd26f8aa5)) but the page returned HTTP 410 Gone on direct fetch — the article may have been deleted or moved, further undermining the evidentiary chain. The mechanism (per-request server compute adds TTFB) is HIGH; the Krishnajlathi numbers are [unverified by direct fetch].

**falsification:** Run a controlled load test using k6 or Gatling at 2× production RPS with identical infrastructure (both origin-served and CDN-cached configurations) and compare p95 TTFB. If p95 stays under 200ms with CDN caching enabled on the RSC build, Analyst A's framing of TTFB regression as a structural constant is falsified.

**severity:** high (structural mechanism is real; severity inflated by evidence quality)
**confidence:** MEDIUM (mechanism is HIGH; specific numbers are [unverified])

### Finding 3 — The "SPA Has Zero Interactivity Gap" Comparison Is a Category Error (Challenge to Analyst A's Finding 2)

**target:** Analyst A

**steelman:** RSC shows visible content sooner than an SPA, but if that content is non-interactive for 2.52 seconds, users clicking CTAs get no feedback — a directly measurable conversion risk on e-commerce pages.

**weakness:** Analyst A states "a pure SPA has **0 s** interactivity gap because nothing renders until JS is ready." The Web Performance Calendar 2025 article — Analyst A's own primary source — explicitly contradicts this. Fetched directly, it states that SPAs have *no measured interactivity gap because the page is blank until JavaScript executes; there is no gap between visibility and interactivity since neither exists initially.* The absence of a gap is not the same as fast interactivity. An SPA on a slow 4G connection with a 400KB bundle has 0ms gap but may have 3–5s Time to Interactive because the entire wait is invisible to the user (blank screen or spinner). RSC shows a product image, price, and "Add to Cart" button at 1.28s LCP, then makes it interactive at 3.8s. The SPA shows nothing until 4.1s and becomes interactive simultaneously. The RSC experience is *better* for users who perceive early content as progress and less likely to bounce — but Analyst A's 0ms baseline turns an architectural trade-off into a fictitious RSC-exclusive penalty. The correct comparison is INP from page initiation, not the gap between FCP and TTI.

**evidence:** Web Performance Calendar 2025 article (fetched directly): "SPAs have no measured interactivity gap because the page is blank until JavaScript executes — there's no gap between visibility and interactivity since neither exists initially." | "The baseline SPA showed 4.1 s LCP" vs RSC "1.28 s LCP." The SPA's 4.1s LCP *is* its TTI — the comparison Analyst A presents as RSC ≫ SPA is inverted for slow-connection users.

**falsification:** Run a RUM study measuring INP from `navigationStart` (not from FCP) on both SPA and RSC builds across the same user cohort on median-connection devices. If RSC shows worse INP-from-start on p75, the interactivity gap matters in the framing Analyst A intends. If RSC shows comparable or better INP-from-start despite a visibility-to-interactivity gap, the finding's severity drops to low.

**severity:** medium (the interactivity gap risk is real on fast connections where RSC provides little FCP advantage; the severity is overstated for slow connections)
**confidence:** HIGH

### Finding 4 — CSS-in-JS Incompatibility Is a Real, Well-Evidenced Forcing Function for "use client" Propagation

**target:** the proposal

**steelman:** Teams that have already adopted Tailwind CSS, CSS Modules, or zero-runtime styling libraries face no compatibility barrier with RSC. Migration effort is bounded to component logic, not styling architecture.

**weakness:** Large e-commerce React SPAs have overwhelming CSS-in-JS adoption. MUI (Material UI) and Chakra UI — the dominant React component libraries for e-commerce teams who want accessible, pre-built product card, modal, and form components — require React `useContext` for theming and browser-side style injection, making them fundamentally incompatible with Server Components. Every component touching a MUI/Chakra primitive requires `"use client"`, which cascades through the import graph. Mux's 50,000-line migration identified this as the dominant rework effort. For an e-commerce site where the design system is built on MUI (product cards, search filters, cart drawer, checkout form), the forced migration from CSS-in-JS to Tailwind or CSS Modules is a months-long rework with its own test coverage gaps and visual regression risk — a migration-within-a-migration that the RSC migration proposal budget almost certainly does not include.

**evidence:** Josh Comeau: "styled-components are designed to run in-browser…every component that renders even a single styled-component needs to become a Client Component." ([joshwcomeau.com/react/css-in-rsc/](https://www.joshwcomeau.com/react/css-in-rsc/).) Mux blog: CSS-in-JS called "probably the biggest part of our RSC conversion." ([mux.com/blog/what-are-react-server-components](https://www.mux.com/blog/what-are-react-server-components).) ProNextJS confirmed MUI and Chakra require `"use client"` wrapping. ([pronextjs.dev/why-doesn-t-material-ui-or-chakra-work-in-the-app-router](https://www.pronextjs.dev/why-doesn-t-material-ui-or-chakra-work-in-the-app-router).) Three independent sources converge. Confidence: HIGH.

**falsification:** Audit the component tree. If fewer than 20% of leaf components by rendered weight depend on a CSS-in-JS library, the forced-migration scope is bounded and severity drops to medium.

**severity:** high
**confidence:** HIGH

### Finding 5 — Client-Side Router Cache Delivers Stale Inventory and Pricing; Server-Side `revalidatePath` Cannot Push Invalidation to Open Tabs

**target:** the proposal

**steelman:** Next.js provides `revalidatePath`, `revalidateTag`, and on-demand ISR. A properly instrumented mutation pipeline ensures stale data windows are bounded and acceptable for e-commerce SLAs.

**weakness:** The Next.js client-side Router Cache stores RSC payloads in the browser tab for 30 seconds (dynamic routes). This cache is separate from the server Data Cache and is not reachable by `revalidatePath` — because the server has no push channel to an already-loaded tab. A user who loads a product page, keeps the tab open, and an inventory change occurs (flash sale ends, stock depletes) will see stale "In Stock" and original pricing for up to 30 seconds even after the server correctly invalidates its own caches. The fix is `router.refresh()` called explicitly at every mutation point — an engineering discipline that is easy to omit on a large team across hundreds of mutation paths. For e-commerce, this is not a UX nuisance; it is a revenue and correctness failure: overselling out-of-stock items, presenting expired promotional prices.

**evidence:** Router cache durations: "Static routes: 5 minutes of client-side cache. Dynamic routes: 30 seconds of client-side cache." (Confirmed in vercel/next.js Discussion #54075.) | "The Router Cache can lead to stale data being displayed as pages are not requested from the server again during navigation." (Multiple sources, WebSearch-confirmed.) Mechanism: HTTP-level cache invalidation cannot reach in-browser JS memory state; only explicit `router.refresh()` does. Confidence: HIGH.

**falsification:** Mark a product out-of-stock server-side and call `revalidateTag`. Without a hard browser refresh, navigate away and back within 30 seconds. If the page shows updated stock, the router cache is being correctly bypassed — test passes. Failing result is the expected default without explicit `router.refresh()` instrumentation.

**severity:** high
**confidence:** HIGH

### Finding 6 — Server-Side Fetch Waterfall Is the Default RSC Composition Pattern and Adds Additive Latency

**target:** the proposal

**steelman:** Server-to-service latency (10–30ms to a co-located database) is far lower than browser-to-API latency (100–300ms). Even with sequential fetches, the absolute latency is lower than the parallel SPA equivalent.

**weakness:** The idiomatic RSC pattern — `await fetchProduct()` in a parent, child renders with `await fetchReviews()` — creates strict sequential execution: child cannot start fetching until parent finishes rendering. On a product detail page with 4–5 independent data sources (product details, inventory, reviews, related products, personalized recommendations), server-side latency is *additive*: if each service call takes 50ms, sequential execution yields 200–250ms of blocking server render time. The equivalent SPA fires all 5 calls in parallel on component mount, with independent loading skeletons, so total data latency equals the *maximum* (50ms). The server-to-service latency advantage is real but does not overcome the additive-vs.-maximum structural difference at scale. Aurora Scharff's post demonstrates that waterfall avoidance requires explicit `Promise.all` or `React.cache()` coordination — both non-idiomatic patterns that require active architectural enforcement on every PR.

**evidence:** "The Comments component cannot start fetching its data before Post is done running the await to fetch its data, even though Comments does not depend on data fetched by the Post component." ([LogRocket RSC pitfalls](https://blog.logrocket.com/react-server-components-performance-mistakes).) "nothing goes to the browser until the slowest request finishes" (ibid.). Aurora Scharff confirms server component waterfall is the default failure mode and requires explicit `cache()` pattern to avoid. ([aurorascharff.no/posts/avoiding-server-component-waterfall-fetching-with-react-19-cache/](https://aurorascharff.no/posts/avoiding-server-component-waterfall-fetching-with-react-19-cache/))

**falsification:** Instrument the migrated product detail page with `Server-Timing` headers and OpenTelemetry traces. If all independent data fetches (`product`, `reviews`, `inventory`, `recommendations`) start within 5ms of each other, parallelism is confirmed and this finding is mitigated.

**severity:** high
**confidence:** HIGH

### Finding 7 — Three Confirmed RSC CVEs Are Real, But Analyst A's "Structurally Likely to Recur" Claim Is Unverified Speculation at HIGH Confidence (Partial Challenge, Partial Endorsement of Analyst A's Finding 6)

**target:** Analyst A (partial)

**steelman:** RSC introduces a server-side deserialization endpoint that is a permanently larger attack surface than a CDN-served SPA bundle. Each new RSC feature adds new deserialization code paths, so future vulnerabilities are plausible.

**weakness:** The CVE citations are confirmed real: CVE-2025-55183 (CVSS 5.3), CVE-2025-55184 (CVSS 7.5), CVE-2025-67779 (CVSS 7.5), and CVE-2026-23864 (CVSS 7.5) are all documented in the react.dev advisory and the GitHub Advisory Database. The attack applies even to apps that define no Server Functions, as confirmed: "Even if your app does not implement any React Server Function endpoints it may still be vulnerable if your app supports React Server Components." This is a genuine, verified attack surface expansion. However, Analyst A's claim that the vulnerability class is "structural and likely to recur" with HIGH confidence is a forward prediction about future software development at an organization — not a current measurement. The React team patched four distinct variants across 8 weeks, suggesting active discovery, but the word "structural" implies the deserialization design itself is unfixable, which is not supported by the advisories (the patches were effective). Downgrade this specific sub-claim to MEDIUM; the finding as a whole remains HIGH.

**evidence:** react.dev advisory (fetched directly): CVE-2025-55183 (5.3 Medium), CVE-2025-55184 (7.5 High), CVE-2025-67779 (7.5 High), CVE-2026-23864 (7.5 High) — all confirmed. "Even if your app does not implement any React Server Function endpoints it may still be vulnerable if your app supports React Server Components." ([react.dev/blog/2025/12/11/denial-of-service-and-source-code-exposure-in-react-server-components](https://react.dev/blog/2025/12/11/denial-of-service-and-source-code-exposure-in-react-server-components).) "Structurally likely to recur" — [unverified]; no architectural analysis from the React team supports this specific prediction.

**falsification:** If the rendering endpoint is placed behind a WAF configured to rate-limit POST requests to the RSC flight endpoint, and automated dependency updates to patched versions are enforced in CI, the exploitability of this class drops substantially. The attack surface expansion claim can be falsified by this control plane.

**severity:** high
**confidence:** HIGH (finding); MEDIUM (the "structurally likely to recur" sub-claim)

### Finding 8 — Infrastructure Cost Arithmetic Contains Unverified Assumptions; Analyst A's MEDIUM Confidence Label Is Correct But the Specific Numbers Are Not Defensible (Challenge to Analyst A's Finding 5)

**target:** Analyst A

**steelman:** RSC shifts rendering work from client devices to servers the operator pays for. For a large site with millions of daily users, this compute cost is real and must be projected against the bundle-size savings.

**weakness:** Analyst A's cost calculation uses "200ms average render time" as the per-request compute duration — a number with no cited source. For a streaming RSC implementation, the server begins flushing the HTML shell before all components finish rendering; the total compute time may be 200ms but the TTFB contribution is much shorter. Additionally, the calculation applies Lambda pricing ($0.00004/vCPU-second) to a "large e-commerce site" — a category that virtually always uses provisioned infrastructure (ECS on EC2, Kubernetes, or Vercel's hosted fleet), not Lambda pay-per-invocation. On provisioned infrastructure, the marginal cost of additional requests within existing capacity is near zero until a scaling event occurs. The relevant cost question is: what is the infrastructure sizing difference at peak load between RSC (origin-computed) and SPA+API (CDN-served shell + origin-computed API calls)? Both architectures make origin API calls for personalization data; only RSC adds origin HTML/RSC payload rendering. That delta — not the full render cost — is the incremental infrastructure cost.

**evidence:** "200ms average render time" — [unverified]; no source cited by Analyst A. Lambda pricing for e-commerce — inapplicable without evidence the site runs on Lambda. Reasoning: both SPA and RSC make origin API calls for personalized data; the incremental compute is RSC component rendering only, which is much less than the total API compute budget. MEDIUM confidence on cost direction is correct; the specific arithmetic is [unverified].

**falsification:** Capture AWS Cost Explorer or equivalent billing data for compute + CDN bandwidth before and after migration for a 7-day window at equivalent traffic. Compare total invoice, not per-request arithmetic.

**severity:** high (the cost inversion mechanism is real for uncached personalized pages; the specific scale is MEDIUM)
**confidence:** MEDIUM

### Finding 9 — PPR (Partial Prerendering) Resolves CDN Bypass Only If Boundary Annotation Is Correct at Scale — An Untested Assumption

**target:** the proposal (new finding)

**steelman:** Next.js 16 (October 2025) shipped Partial Prerendering as stable, allowing a static HTML shell to be edge-cached while dynamic holes stream from origin. This directly fixes the CDN bypass problem for initial page loads and makes the performance model more predictable.

**weakness:** PPR's correctness depends on every piece of personalized or dynamic content being wrapped in a `<Suspense>` boundary that is correctly classified as dynamic. For a large e-commerce site with A/B testing (which touches layout, CTAs, and pricing), geolocation-based pricing, user-specific loyalty badges, and real-time inventory indicators scattered across dozens of components, the number of sites requiring dynamic annotation is large. A single missed annotation either (a) serves stale personalized content from the CDN shell (correctness failure — wrong user sees wrong loyalty tier or price), or (b) causes the entire page to fall back to full dynamic rendering (performance regression). Additionally, PPR was experimental through Next.js 14–15 and reached production stability only in Next.js 16, meaning sites currently mid-migration to an earlier Next.js version must plan an additional upgrade hop. Client-side navigation between PPR pages still issues RSC payload requests that bypass CDN for dynamic holes (the `?_rsc=` problem from Finding 2 in my original analysis persists for dynamic segments), so CDN relief is partial: full-page loads benefit; navigation does not.

**evidence:** PPR stable status confirmed: "PPR was introduced as experimental in Next.js 14, refined in Next.js 15, and shipped as stable in Next.js 16 (October 2025)." ([samcheek.com/blog/nextjs-partial-prerendering-production-2026](https://samcheek.com/blog/nextjs-partial-prerendering-production-2026).) Next.js documentation confirms `<Suspense>` boundary annotation as the mechanism. ([nextjs.org/docs/15/app/getting-started/partial-prerendering](https://nextjs.org/docs/15/app/getting-started/partial-prerendering).) The `_rsc` CDN bypass for dynamic segments persists even with PPR for client-side navigation (reasoning: PPR's static shell is the full-page request; the incremental RSC payload for subsequent navigations remains dynamic-only).

**falsification:** Instrument CDN logs for a PPR-enabled product category page. Measure cache hit ratio for both (a) direct URL navigations and (b) client-side navigations from the homepage. If (a) shows ≥ 80% CDN hit rate and (b) shows ≥ 40% hit rate, PPR has materially solved the caching problem at acceptable boundary annotation cost.

**severity:** high
**confidence:** HIGH

### Finding 10 — Async Server Component Unit-Test Gap Forces Business Logic into Slow E2E Feedback Loops

**target:** the proposal

**steelman:** E2E tests (Playwright) cover the full request lifecycle and are the appropriate test layer for components that span the server/client boundary. Modern Playwright is fast enough for critical path coverage.

**weakness:** Pricing rule evaluation, promotional discount application, inventory threshold logic, and regional tax computation are deterministic functions of input — ideal unit test candidates. But when these live inside async server components, they cannot be unit-tested: "async Server Components are new to the React ecosystem, Vitest currently does not support them." The correct fix — extracting logic into pure utility functions called *by* server components — is a refactor that must be explicitly planned and executed. Without it, regression tests for the highest-risk business logic require full browser spin-up (2–5 minutes per Playwright run) rather than sub-second Vitest execution. For a 20–50 engineer team shipping daily, this materially degrades CI feedback on the code paths where bugs cost the most revenue.

**evidence:** "async Server Components are new to the React ecosystem, Vitest currently does not support them. While you can still run unit tests for synchronous Server and Client Components, we recommend using E2E tests for async components." (Next.js documentation, confirmed via GitHub vitest-dev/vitest issue #8526.)

**falsification:** If business logic is fully extracted into pure utility functions (testable via Vitest without async component wrappers) before migration, and coverage metrics confirm 100% of pricing/inventory paths are unit-covered, the velocity impact is mitigated. The refactor cost must be counted in the migration budget.

**severity:** medium
**confidence:** HIGH

### Finding 11 — Global Cart/Session State Forces "use client" to Layout Root, Collapsing RSC Surface on All High-Value Pages

**target:** the proposal

**steelman:** Cart and session state can be managed server-side via cookies or database, threaded as props rather than Context, eliminating the need for a root-level client provider.

**weakness:** React Context is explicitly unavailable in server components. In any real e-commerce SPA, cart state is rendered in the persistent header (cart count), on every product card (add-to-cart), and in the mini-cart overlay. A `CartProvider` wrapping the layout root forces the entire layout subtree to be client-rendered, which includes every product page, category page, and search results page — precisely the pages where RSC bundle savings were supposed to materialize. Migrating cart state from Context to server-computed cookies or URL state is architecturally sound but operationally expensive: it requires rewriting cart mutation logic, updating optimistic UI patterns, and re-testing checkout integrity across device types. The migration proposal that does not explicitly budget this rearchitecture will discover it is necessary mid-migration.

**evidence:** "In Next.js, React Server Components don't support creating or consuming context directly. If you try to create a context in a Server Component, it will result in an error." (Vercel Knowledge Base, WebSearch-confirmed.) Mux blog: "You can access React Context only in Client Components," forcing architectural workarounds. ([mux.com/blog/what-are-react-server-components](https://www.mux.com/blog/what-are-react-server-components).)

**falsification:** Produce a component tree diagram for the migrated app's root layout showing `"use client"` boundaries. If cart/session state boundaries appear no higher than 2 levels below the root (e.g., cart is isolated to a header island), and category and product pages show server-rendered majority by bundle analysis, this finding is mitigated.

**severity:** medium
**confidence:** HIGH
