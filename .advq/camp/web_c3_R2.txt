### **Finding 5: Autovacuum Default Inadequacy — Threshold Calculation Requires Dead Tuple Rate**

**target:** Analyst A, Finding 5

**steelman:** Analyst A argues that default `scale_factor=0.2` means a 10k-row queue table requires 2,050 dead tuples before vacuum triggers, which is reached in seconds at 50 workers.

**weakness:** The calculation is correct *if dead tuple creation is fast*. 50 workers × 10 jobs/sec = 500 jobs/sec. Each job creates one `UPDATE status='in_progress'` (1 dead tuple) and one `UPDATE/DELETE status='done'` (1 dead tuple) = 2 dead tuples/job = 1,000 dead tuples/sec. So yes, 2,050 threshold is breached in ~2 seconds. **However, this assumes autovacuum does not run in the interim.** The autovacuum trigger is `threshold + (live_row_count * scale_factor)`. If the table starts with 10,000 live rows, autovacuum runs at 50 + (10,000 × 0.2) = 2,050 dead tuples. But by the time autovacuum finishes, there may be another 1,000 dead tuples created. The real issue is not the trigger threshold, but the **vacuum_cost_delay (default 2ms per page)** throttling cleanup slower than creation during heavy write load. Analyst A conflates two separate problems: (1) trigger threshold is high (true but not the bottleneck), and (2) vacuum throughput is limited (the real problem). The proposal's mitigation is not "lower scale_factor to 0.01" alone, but "set cost_delay=0 or vacuum_cost_limit=unlimited" on the queue table. Analyst A's evidence cites PlanetScale's dead tuple counts but does not show what scale_factor, cost_delay, or cost_limit they used to measure that.

**evidence:** PostgreSQL documentation (verified): `autovacuum_vacuum_cost_delay` default is 2ms, `autovacuum_vacuum_cost_limit` default is 200. Analyst A's threshold calculation is correct. However, the PlanetScale article does not disclose their autovacuum configuration, so the 383k dead tuple count may have been measured *with* aggressive tuning already partially applied.

**falsification:** Run a 50-worker queue at 50 jobs/sec with default autovacuum settings for 5 minutes, then with `autovacuum_vacuum_cost_delay=0` and `scale_factor=0.01`. If dead tuples remain <10k sustained in the second case, then tuning (not a design flaw) is the mitigation. If dead tuples still exceed 50k even with cost_delay=0, then the design is inadequate.

**severity:** **high → medium** (the problem is real, but it is an operations/tuning problem, not a design flaw; default settings are admittedly inadequate, but the fix is documented and straightforward)

**confidence:** HIGH

## FINAL VERDICT

**The proposal is acceptable if and only if:**

1. **Job Recovery**: Implements heartbeat column (`next_heartbeat`), reaper process checking `next_heartbeat < now()`, and TTL-based re-queue. No job processing inside the lock-holding transaction.

2. **Indexing**: Creates composite index `ON jobs (status, created_at DESC)` with partial predicate `WHERE status = 'pending'` to eliminate table scans.

3. **Autovacuum**: Sets per-table overrides: `autovacuum_vacuum_scale_factor = 0.01`, `autovacuum_vacuum_cost_delay = 0`, `autovacuum_max_workers = 1 (dedicated)` on jobs table.

4. **Polling**: Adds uniformly-distributed jitter of ±50ms to each worker's 100ms interval to eliminate synchronized bursts.

5. **Monitoring**: Establishes alerts on `pg_stat_user_tables.n_dead_tup > (live_row_count * 0.25)`, `LWLock:MultiXact* > 5% of wait time`, and queue depth exceeding 10× steady-state rate.

6. **Version Verification**: Confirms target PostgreSQL version (≥14 recommended) and tests for Steven Winfield's double-processing race in the specific version under load.

7. **Schema Safety**: Implements `lock_timeout = 500ms` on all migration sessions and uses `CREATE INDEX CONCURRENTLY` for all index additions.

If *any one* of these conditions is absent, the system will exhibit one or more of: silent job loss, double-processing, MVCC bloat, or operational deadlock within 24 hours under realistic production load.
