## Final Consolidated Analysis: JWT Tokens in localStorage for SPA

---

### Finding 1

- **severity**: critical
- **confidence**: HIGH
- **target**: proposal; reinforcing Analyst A's first finding with a refinement
- **steelman**: localStorage is simple, framework-agnostic, persists across reloads, and avoids CSRF-related cookie configuration. The team will enforce CSP and review third-party dependencies.
- **weakness**: Any JavaScript execution within the origin — XSS (reflected, stored, DOM-based), a compromised npm dependency, an injected analytics tag, or a malicious ad creative — trivially exfiltrates both tokens via `localStorage.getItem()`. The refresh token is the catastrophic loss: it converts a transient, one-shot XSS into durable, off-device account takeover lasting the token's full lifetime (often days to weeks). No browser mechanism exists to restrict JavaScript read-access to localStorage keys — there is no analog to `httpOnly`. This is the central, load-bearing hidden assumption of the entire design: **the application and all its transitive dependencies will be free of any XSS for the lifetime of deployment**. This is not demonstrable; you can only show the absence of known XSS at a point in time, and every commit and dependency update resets the clock. **Challenge to Analyst A**: I agree with the core finding but note that Analyst A's inclusion of "malicious browser extensions with page access" inflates the differential argument. Extensions with `webRequest` permissions can also intercept `httpOnly` cookies in transit (reading the `Cookie` header on outgoing requests). The extension attack surface applies to *both* storage mechanisms, not uniquely to localStorage. The argument is already conclusive on XSS alone; weakening it with an extension vector that partially applies to the alternative undermines the otherwise clean reasoning.
- **evidence**: OWASP's guidance on token storage explicitly warns against localStorage due to XSS accessibility. The Web Storage spec (WHATWG) provides no access-control mechanism beyond same-origin policy. The `event-stream` npm incident (2018) demonstrated that supply-chain compromise can inject credential-stealing code into legitimate packages. Attack chain: XSS injection → `localStorage.getItem('refresh_token')` → exfiltration to attacker-controlled endpoint → offline token replay → persistent account takeover.
- **falsification**: Demonstrate a browser API or Web Storage feature that restricts JS read-access to specific localStorage keys. Alternatively, show that tokens are cryptographically sender-constrained (e.g., via DPoP per RFC 9449), making exfiltrated tokens unusable on another device.

### Finding 2

- **severity**: critical
- **confidence**: HIGH
- **target**: proposal; reinforcing Analyst A's third finding with scope expansion
- **steelman**: Attaching the token to every request via a global interceptor simplifies the auth layer and prevents accidentally unauthenticated requests to the first-party API.
- **weakness**: The word "every" conceals a dangerous hidden assumption: that the application will only ever issue network requests to trusted first-party origins. Real SPAs issue requests to analytics endpoints, error-reporting services (Sentry, Datadog), feature-flag providers, CDN-hosted resources, image/file proxies, and tenant-controlled URLs. A global Axios interceptor or Angular `HttpInterceptor` applies to all outbound requests unless the developer builds and maintains an explicit origin allowlist. Any miss — a new integration, a data-driven URL, a tenant-supplied endpoint — silently leaks valid bearer tokens. Unlike cookie-based auth, where `Domain`/`Path`/`SameSite` scoping is enforced by the browser, header-based auth relies entirely on application-level filtering with no browser backstop. Analyst A correctly identifies this and provides the right falsification (exact-origin allowlist), which I endorse.
- **evidence**: Standard interceptor APIs (`axios.interceptors.request.use`, Angular's `HttpInterceptor`, `fetch` wrapper) operate on all matching requests by default. The `fetch` API has no built-in "attach this header only to same-origin requests" flag. The probability of a scoping miss increases monotonically with team size, project age, and number of third-party integrations.
- **falsification**: Enumerate every code path issuing network requests and verify the interceptor checks against an explicit, tested origin allowlist. If this exists and is enforced via CI/linting, this specific weakness is mitigated.

### Finding 3

- **severity**: high
- **confidence**: HIGH
- **target**: proposal (refresh token in JS-accessible storage)
- **steelman**: Storing the refresh token client-side enables silent token renewal without full-page redirects, improving UX. Keeping both tokens client-side avoids server-side session state.
- **weakness**: This design treats access and refresh tokens as having equivalent storage-security requirements. They do not. The access token's short TTL (~5–15 minutes) bounds the exploitation window from exfiltration. The refresh token's long TTL (days to weeks) removes that bound. Placing the refresh token in localStorage means any single XSS event grants the attacker the ability to mint new access tokens from their own device for the refresh token's full lifetime. The hidden assumption is that a server-side revocation mechanism exists. But many JWT architectures are chosen precisely to avoid server-side state — creating a direct contradiction. If refresh tokens are stateless (no server-side revocation list), the user and the security team have *no mechanism* to invalidate a stolen refresh token. RFC 6749 §10.4 states refresh tokens "MUST be kept confidential" and recommends binding them to the client. A browser SPA cannot hold a client secret, so this binding is architecturally impossible without additional mechanisms like DPoP. The IETF's OAuth 2.0 for Browser-Based Apps document (Parecki, Waite) recommends the backend-for-frontend (BFF) pattern instead.
- **evidence**: Attack chain: XSS → exfiltrate refresh token → attacker calls `/token` endpoint from separate machine → receives new access tokens → maintains access for days/weeks, independent of victim's session. RFC 6749 §10.4 on refresh token confidentiality. The OAuth 2.0 for Browser-Based Apps draft explicitly recommends against storing refresh tokens in browser-accessible storage.
- **falsification**: Confirm the backend implements refresh token rotation with family-based reuse detection (per the OAuth Security BCP). Even then, the attacker may use the stolen token *before* the legitimate client rotates, so this mitigates but does not eliminate risk.

### Finding 4

- **severity**: high
- **confidence**: HIGH
- **target**: proposal; partially challenging Analyst A's second finding (severity)
- **steelman**: Refresh token rotation with single-use semantics prevents stolen tokens from being reused.
- **weakness**: Analyst A correctly identifies the multi-tab race condition on refresh tokens (HIGH severity). **I partially challenge the severity.** The security dimension — backends relaxing single-use enforcement to avoid races — is real but is a *backend implementation choice*, not an inherent consequence of the localStorage proposal. A well-designed rotation scheme with a short grace period (accepting both old and new refresh tokens for a ~30-second window during rotation) handles multi-tab concurrency without compromising security. The client-side coordination problem (using `BroadcastChannel` or `localStorage` events to synchronize refresh across tabs) is solvable engineering. The *availability* dimension (spurious 401s, logout loops) is real but is **medium** severity — it degrades UX, not security. I'd rate this finding **high** overall only because the *common* backend response to this race is to weaken rotation guarantees, which is a security regression. But this is a conditional severity: it's high *because teams usually get it wrong*, not because it's architecturally inevitable.
- **evidence**: The `BroadcastChannel` API (supported in all modern browsers) allows tabs to coordinate refresh operations. The `storage` event on `localStorage` changes can serve the same purpose. These coordination mechanisms exist and are well-documented. The race condition is a solved problem in client-side engineering — the concern is that most teams don't solve it and instead weaken the backend.
- **falsification**: Implement a mutex-like refresh coordinator (leader election via `BroadcastChannel` or `localStorage` lock) and run a chaos test: 5+ tabs, forced token expiry, simultaneous API calls. If exactly one refresh succeeds and all tabs converge without logout, the availability concern drops. Then verify the backend still enforces single-use rotation — if it does, both dimensions are addressed.

### Finding 5

- **severity**: high
- **confidence**: MEDIUM
- **target**: proposal; reinforcing Analyst A's fourth finding
- **steelman**: Bearer tokens are standard, work well over TLS, and avoid the complexity of cookie-based auth.
- **weakness**: Bearer semantics mean possession equals authorization. The hidden assumption is that no system in the request path logs, caches, or records the `Authorization` header. In practice, reverse proxies (nginx `$http_authorization`), API gateways, WAFs, APM tools, error-reporting services (which capture request metadata), and even browser DevTools network exports all may record bearer tokens. Because the design attaches the token to *every* call, the number of request-response pairs carrying credentials is maximized, and each is an opportunity for leakage. A leaked access token from server logs is usable until expiry; a leaked refresh token from a crash dump or exported HAR file is usable for days. This is compounded by the fact that operational teams outside the security perimeter (SREs, support engineers) often have access to these logs.
- **evidence**: nginx logs `$http_authorization` if included in the log format. HAR file exports from browser DevTools include all request headers by default. Sentry's default SDK configuration captures request headers unless explicitly scrubbed. Each of these is a documented default behavior, not an edge case. The attack does not require breaking crypto or browser isolation — it requires reading a log file.
- **falsification**: Trace an authenticated request end-to-end through every layer (browser instrumentation, CDN, WAF, ingress controller, API gateway, application logs, APM, error reporting). If the `Authorization` header is redacted at every layer and this redaction is enforced by policy and tested in CI, this concern drops.

### Finding 6

- **severity**: medium
- **confidence**: HIGH
- **target**: proposal (localStorage persistence without expiration)
- **steelman**: localStorage persistence improves UX: auth survives reloads, browser restarts, and tab restoration.
- **weakness**: localStorage has no expiration mechanism — the Web Storage spec defines no TTL or `Max-Age` attribute. Token cleanup depends entirely on application JavaScript executing correctly on every exit path. Hidden failure modes: (1) user closes tab/browser without "logout" (the common case); (2) app JavaScript fails to load (CDN outage, JS error); (3) user clears cookies but not localStorage (browser UIs are inconsistent — Chrome clears localStorage with "Cookies and other site data" but users often don't understand this grouping); (4) device is shared, lost, or stolen — tokens are readable in DevTools → Application → Local Storage with zero technical skill. On a kiosk or shared machine, this is trivially exploitable. Analyst A's finding on shared devices is correct and I reinforce it.
- **evidence**: The WHATWG Web Storage spec defines `setItem(key, value)` with no TTL parameter. Browser "Clear browsing data" behavior varies: Firefox separates cookies from "Offline website data" (which includes localStorage). The `sessionStorage` alternative clears on tab close but doesn't persist across tabs — creating a UX trade-off the proposal does not acknowledge.
- **falsification**: Show that the application wraps localStorage with expiration checks on every read, and that this wrapper is the exclusive access path (enforced by linting). Even then, tokens remain on disk between reads.

### Finding 7

- **severity**: medium
- **confidence**: HIGH
- **target**: proposal (stateless JWT revocation gap)
- **steelman**: JWTs are self-contained and validated without database lookups, enabling stateless, horizontally scalable APIs.
- **weakness**: The design hides a contradiction. JWTs are chosen for statelessness, but security-critical operations — logout, password reset, account suspension, privilege changes, compromise response — all require immediate token invalidation, which requires server-side state (a blocklist). If the backend is truly stateless, a banned user's access token remains valid until `exp`. If the backend maintains a revocation list, it has reintroduced per-request state lookups, negating the statelessness advantage. This is especially dangerous combined with Finding 3: the refresh token lets the attacker *continuously mint new valid access tokens* even after the user changes their password, unless the refresh token is also tracked and revocable server-side. RFC 8725 (JWT BCP) §3 [unverified specific section number] acknowledges that JWTs are not easily revocable. Analyst A's finding on this is correct; I add that the *combination* of irrevocable access tokens and irrevocable refresh tokens in a JS-readable store creates a failure mode where incident response is effectively impossible without rotating the signing key (which invalidates *all* users' sessions).
- **evidence**: JWT RFC 7519 defines `exp` but no revocation mechanism. Revocation requires external infrastructure (e.g., Redis blocklist checked on every request), which is per-request state — equivalent in cost to session-based auth. The signing-key rotation nuclear option is the only stateless revocation mechanism and it is indiscriminate.
- **falsification**: Confirm: (1) access token lifetime ≤2 minutes; (2) refresh token rotation with reuse detection is implemented; (3) a per-request revocation check exists for the refresh token endpoint. If all three hold, the revocation gap is bounded to 2 minutes — acceptable for most threat models but no longer stateless.

### Finding 8

- **severity**: medium
- **confidence**: HIGH
- **target**: Analyst A's CSRF/XSS trade finding; strengthening it
- **steelman**: Using JWTs in `Authorization` headers avoids CSRF because the browser doesn't send them ambiently like cookies. This is a net security improvement over cookie-based auth.
- **weakness**: **Analyst A understates this.** Calling it "only a trade, not a free win" implies rough equivalence. It is not a trade — it is a strictly worse position in most SPA threat models. CSRF attacks are *constrained*: the attacker can trigger state-changing actions but cannot read responses (same-origin policy) and cannot exfiltrate credentials. XSS attacks are *unconstrained within the origin*: the attacker can read all data, exfiltrate credentials, impersonate the user indefinitely, and maintain access after the session ends. Swapping CSRF exposure (mitigable with `SameSite=Strict` cookies, which is a single attribute) for elevated XSS exposure (credential theft, not just action replay) is a net downgrade. The hidden assumption is that XSS and CSRF are comparable threats — they are not. XSS strictly dominates CSRF in attacker capability. Modern browsers' `SameSite=Lax` default (Chrome since 2020, Firefox since 2022 [unverified exact date]) already mitigates most CSRF without any application-level work, further reducing the value of the CSRF protection gained.
- **evidence**: CSRF: attacker triggers actions, cannot read responses or exfiltrate credentials. XSS with localStorage tokens: attacker reads all DOM content, exfiltrates tokens, maintains persistent access. The asymmetry is structural, not incidental. Chrome defaulted `SameSite` to `Lax` in version 80 (February 2020), making cookie-based CSRF significantly harder without any application changes.
- **falsification**: Show that the application's actual threat surface has zero script-injection paths (no user-generated content, no third-party scripts, no DOM sinks, no rich text editors, no markdown renderers) AND that the CSRF risk would be severe without header-based auth. If both conditions hold, the trade may be favorable for this specific application.

### Finding 9

- **severity**: medium
- **confidence**: MEDIUM
- **target**: proposal (hidden assumption: bearer tokens need no sender-constraining)
- **steelman**: Bearer token semantics are simple and universally supported — any HTTP client can present the token.
- **weakness**: The proposal implicitly assumes that token possession should equal authorization — that no binding between the token and the client device is needed. This assumption is what makes every other finding exploitable: XSS exfiltration works because the token is usable on another machine; log leakage works because anyone reading the log can replay the token; shared-device exposure works because the next user can use the token as-is. RFC 9449 (DPoP — Demonstrating Proof-of-Possession) exists precisely to address this gap: it binds tokens to a client-generated keypair so that the token alone is insufficient without the corresponding private key. If the SPA used DPoP with a non-exportable `CryptoKey` (via the Web Crypto API's `extractable: false`), exfiltrated tokens would be unusable without the key, which cannot be extracted from the browser. This is a missing mitigation that would substantially reduce the impact of Findings 1, 3, 5, and 6.
- **evidence**: RFC 9449 defines DPoP for exactly this threat model. The Web Crypto API allows generating non-exportable keys (`crypto.subtle.generateKey(..., false, ['sign'])`) that cannot be read by JavaScript — only used for signing operations. This creates an asymmetry: the SPA can prove possession of the key without the key being exfiltrable, even under XSS. The hidden assumption is that this mechanism is either unnecessary or impractical — but it is standardized and supported in all modern browsers.
- **falsification**: If the API does not support DPoP and cannot be modified, or if the `CryptoKey` non-exportability guarantee has known bypasses in major browsers, this mitigation is impractical and the finding reduces to "the proposal lacks a mitigation that exists but may not be deployable."

### Finding 10

- **severity**: low
- **confidence**: MEDIUM
- **target**: proposal; reinforcing Analyst A's eighth finding
- **steelman**: A single localStorage-based token store is simple to reason about and easy to integrate.
- **weakness**: Simplicity breaks down with multiple execution contexts (tabs, service workers, web workers, microfrontends). `localStorage` operations are synchronous and blocking but lack transactional semantics across contexts. The `storage` event fires only in *other* tabs, not the tab that wrote. A refresh operation in Tab A writes a new token; Tab B, mid-flight with the old token, gets a 401; Tab B reads the new token from localStorage but also initiates its own refresh (if the interceptor retries with refresh); now two refreshes race. The coordination problem is solvable (Finding 4 discusses `BroadcastChannel`) but the proposal does not acknowledge it, and most implementations don't solve it. The practical consequence is intermittent, hard-to-reproduce auth failures in production.
- **evidence**: The Web Storage spec: `storage` events fire in other browsing contexts sharing the same origin, not in the context that made the change. This means the writing tab has no event-driven notification mechanism for other tabs' state — coordination must be built explicitly. The `BroadcastChannel` API is the appropriate mechanism but requires deliberate implementation.
- **falsification**: Multi-tab chaos test under forced token expiry with timing instrumentation. If auth state converges without spurious 401s or refresh storms, the concern is academic.

---

## Acceptance Condition

This design is acceptable **only if all** of the following hold simultaneously: (1) tokens are moved to `httpOnly`, `Secure`, `SameSite=Strict` cookies or a BFF pattern, removing JS-readable credential storage entirely — **or** sender-constraining (DPoP with non-exportable `CryptoKey`) is implemented so that exfiltrated tokens are unusable; (2) the request interceptor is scoped to an explicit, tested, CI-enforced origin allowlist; (3) refresh token rotation with reuse detection is implemented server-side and proven under multi-tab concurrency; (4) access token lifetime ≤5 minutes; (5) a server-side revocation mechanism exists for refresh tokens and is exercised on logout, password change, and account suspension; and (6) the `Authorization` header is verified to be redacted at every observability and logging layer. Absent any one of these, the architecture contains a concretely exploitable flaw that does not require a sophisticated attacker.
