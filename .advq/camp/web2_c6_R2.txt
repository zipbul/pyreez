## Final Consolidated Severity-Ordered List

---

### CRITICAL

**Finding C1 — CDN Caching Architecture Structurally Broken for RSC Navigation Payloads**

*target:* The proposal

*steelman:* RSC pre-renders at the server and can be CDN-cached, surpassing a SPA that always demands a JS bundle plus client-side data fetch.

*weakness:* Client-side navigations in Next.js App Router generate RSC payloads via `_rsc` query parameters whose hash value is derived from the navigation source path, not destination content. Two navigations to `/product/299336` from different source pages produce `/product/299336?_rsc=1vl30` and `/product/299336?_rsc=qe3go` — identical server responses, distinct cache keys. The `Vary` header emitted (`Vary: RSC, Next-Router-State-Tree, Next-Router-Prefetch, Next-Url`) reflects source navigation state, further breaking CDN matching. Every client-side navigation becomes an origin request. For a catalog of 100,000 product pages with high navigation frequency, RSC payload CDN cache hit rate approaches zero, fully eliminating the caching advantage and inflating origin compute costs.

*evidence:* Verified GitHub discussion documents exact behavior: navigations produce "product/299336/?_rsc=1vl30 and product/299336/?_rsc=qe3go return identical data despite different hashes" with "absolutely no cache." — [vercel/next.js Discussion #59167](https://github.com/vercel/next.js/discussions/59167)

*falsification:* Deploy behind a CDN with analytics; measure RSC payload cache hit rate across 1,000 realistic browsing navigations. Hit rate > 50% falsifies; hit rate ~0% confirms.

*severity:* critical
*confidence:* HIGH

---

**Finding C2 — Every Client Navigation Now Pays Full Origin Round-Trip Latency**

*target:* The proposal

*steelman:* RSC moves data fetching to the server before streaming; with Suspense the first byte arrives faster than a SPA's JS-parse-then-fetch cycle.

*weakness:* In the SPA, client-side routing is a local state transition — zero network cost. Post-migration, every in-app navigation triggers a server round-trip for the RSC payload. A user 200 ms RTT from the origin (Southeast Asia to US-East origin, a realistic enterprise scenario) pays 200–400 ms on every product-to-category or category-to-PDP click, regardless of whether the destination content has changed. The perfplanet.com analysis found that SSR with server-side data fetching (1.78 s LCP) is *slower* than SSR with client-side fetching (1.28 s LCP) — server-side data fetching only wins on LCP when compared to unoptimized full-page renders, not when compared to a well-structured SPA.

*evidence:* Perfplanet.com (fetched this session): SSR with server data fetching LCP = 1.78 s; SSR with client data fetching = 1.28 s. "You'll only see performance benefits from Server Components if data fetching is involved." — [Web Performance Calendar 2025](https://calendar.perfplanet.com/2025/intro-to-performance-of-react-server-components/)

*falsification:* Measure p50/p95 click-to-render time under SPA vs. RSC for a user 150 ms RTT from origin. If RSC is equivalent or faster, finding weakens.

*severity:* critical
*confidence:* HIGH

### HIGH

**Finding H1 — `use client` Boundary Creep Collapses Bundle-Size Gains for Interactive E-Commerce**

*target:* The proposal

*steelman:* Fine-grained server/client splitting allows product descriptions and metadata to stay server-only while only interactive leaf nodes ship JS.

*weakness:* E-commerce is interaction-dense: faceted filters, carousels, cart drawers, live stock indicators, coupon inputs, countdown timers, A/B CTAs. Each mandates `use client`. Critically, any import into a client module marks the entire import subtree as client-side. More severe: Emotion (used by MUI, one of the most widely adopted enterprise React UI libraries) has an open GitHub discussion dating to 2023 with no RSC support and a core maintainer implying it is architecturally incompatible. I fetched Discussion #3119 directly: "Emotion will likely always rely on client-side JS." A large SPA built on MUI/Emotion must either (a) wrap every component in `use client` (net zero bundle saving) or (b) run a parallel styling migration to CSS Modules/Tailwind — a months-long project orthogonal to the RSC migration.

*evidence:* Emotion Discussion #3119 (fetched): RSC support is architecturally blocked by Emotion's runtime JS requirement. — [emotion-js/emotion Discussion #3119](https://github.com/emotion-js/emotion/discussions/3119). Styled-components v6.3.0 (January 2026) added RSC support, but Emotion has not. LogRocket: over-using `use client` is pitfall #1 for bundle size negation. — [LogRocket](https://blog.logrocket.com/react-server-components-performance-mistakes)

*falsification:* Count the fraction of component tree nodes requiring `use client` or importing Emotion-based components. If < 30% of tree weight is client-bound, savings are plausible; if > 60%, the migration thesis collapses.

*severity:* high
*confidence:* HIGH

---

**Finding H2 — Router Cache Stale Pricing/Inventory Is a Correctness Failure**

*target:* The proposal

*steelman:* Server Actions + `revalidatePath`/`revalidateTag` give fine-grained cache invalidation superior to SPA refetch-on-mount.

*weakness:* `revalidatePath` and `revalidateTag` flush server-side caches but do *not* flush the client-side Router Cache in active browser tabs. Dynamic pages are cached in the Router Cache for 30 seconds; static pages for 5 minutes. A user navigating away from a product page and returning within that window sees a stale RSC payload even after server-side price or stock updates. For e-commerce, displaying $299 when the item repriced to $349, or showing "In Stock" after sell-out during a flash sale, has direct legal and commercial consequences.

*evidence:* Verified GitHub discussion: "The Router Cache can lead to stale data being displayed on pages, as pages are stored for 30 seconds if dynamic and five minutes if static, and the cache cannot be revalidated unless the user hard-reloads the page." — [vercel/next.js Discussion #54075](https://github.com/vercel/next.js/discussions/54075)

*falsification:* Update a price on the server, trigger `revalidatePath`, then client-navigate to the product from a tab that has it in Router Cache. Inspect the displayed price. Stale = confirmed.

*severity:* high
*confidence:* HIGH

---

**Finding H3 — Nested Async Components Produce Sequential Server-Side Fetch Waterfalls**

*target:* The proposal (and Analyst A Finding 6 — but the mechanism A identifies as "the default coding pattern produces the worst outcome" is the substantive point; I add that the fix is architecturally regressive)

*steelman:* Co-locating data fetching with components eliminates prop-drilling and over-fetching; `Promise.all` enables parallelism.

*weakness:* Sequential `await` at component boundaries prevents children from beginning their fetches until parents resolve — a waterfall the component-colocation pattern actively encourages. For a product page with auth check → product data → recommendations → inventory (each a separate service), sequential awaits produce 50+80+60+40 = 230 ms server latency before streaming begins, on independent fetches. The fix — hoisting all fetches to a common parent and passing promises down — reintroduces prop-drilling in a different form. Teams under delivery pressure choose the legible sequential pattern; the architectural discipline required to prevent waterfalls is not enforced by the framework. This is a "pit of failure" not a "pit of success."

*evidence:* Kent C. Dodds (Epic React, fetched in prior session): "both `searchShips` and `getShip` won't be executed until *after* `getLoggedInUser` resolves, even though those don't directly depend on the user." — [epicreact.dev/server-waterfall-problem-rscs](https://www.epicreact.dev/server-waterfall-problem-rscs)

*falsification:* Profile server-side fetch timeline for the top-5 page types using distributed tracing. If independent fetches co-start within 5 ms, waterfall is not present.

*severity:* high
*confidence:* HIGH

**Finding H4 — Async Server Components Are Untestable with Vitest, Collapsing CI Discipline**

*target:* The proposal

*steelman:* RSC logic runs in Node.js, making it testable without DOM simulation.

*weakness:* Vitest — the current industry-standard unit test runner — explicitly does not support async Server Components. The official Next.js docs state: "we recommend using E2E tests for `async` components." E2E tests (Playwright/Cypress) are 10–100x slower per test, require a running server, and demand browser infrastructure in CI. A large e-commerce team with hundreds of component tests faces three losing choices: no unit tests for async server components, synchronous rewrites that surrender data co-location, or a full E2E migration that destroys CI throughput.

*evidence:* Direct verbatim from official Next.js docs (fetched 2026-06-01): "Since `async` Server Components are new to the React ecosystem, Vitest currently does not support them… we recommend using **E2E tests** for `async` components." — [nextjs.org/docs/app/guides/testing/vitest](https://nextjs.org/docs/app/guides/testing/vitest)

*falsification:* Check whether the version of Vitest available at migration time has merged async Server Component rendering support. Track at Vitest GitHub.

*severity:* high
*confidence:* HIGH

### MEDIUM

**Finding M1 — Server Actions Add Network-Round-Trip Tax on Every Mutation; `useOptimistic` Doesn't Cover E-Commerce's Unsafe Cases**

*target:* The proposal

*steelman:* Server Actions eliminate REST boilerplate with co-located RPC; `useOptimistic` provides instant UI feedback.

*weakness:* Every Server Action is a network request — add-to-cart, coupon application, quantity update. Optimistic updates via `useOptimistic` require explicit rollback logic and are *unsafe* for stock-dependent operations (cart may fail if item sold out), server-computed prices (client-side estimate may differ), and coupon validation (server must confirm). These are the exact high-frequency mutations in e-commerce. The SPA's existing Redux/Zustand + explicit API confirmation pattern already handles these correctly; Server Actions require the team to re-implement the same logic under a new paradigm with less ecosystem tooling.

*evidence:* SitePoint: "not every mutation benefits from optimistic UI — should be skipped for irreversible actions, conflict-prone writes, and server-computed transforms." — [SitePoint](https://www.sitepoint.com/react-useoptimistic-production-patterns-for-instant-ui-updates/)

*falsification:* Measure p50 click-to-cart-badge-increment time pre- and post-migration on a 30 ms RTT connection. If within 50 ms, optimistic updates are working. If > 200 ms delta, UX is measurably degraded.

*severity:* medium
*confidence:* HIGH

**Condition under which the proposal is acceptable:**
The migration is acceptable when: (1) the styling layer has already migrated away from Emotion/MUI to CSS Modules or Tailwind (or the team has budgeted a parallel migration); (2) a CDN caching strategy specifically addressing the `_rsc` hash problem is in place before launch, not after; (3) a pre-migration audit confirms fewer than ~30% of page-tree nodes by bundle weight require `use client`; (4) origin and primary database are co-located in the same region, keeping origin TTFB under 80 ms; (5) cache invalidation policy per route is explicitly documented with zero reliance on Router Cache defaults for pricing/inventory routes; and (6) the CI pipeline budget accommodates E2E coverage for async server components.
