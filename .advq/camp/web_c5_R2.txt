### **Finding 1: Cross-Datacenter Replication Breaks Exactly-Once — The Guarantee Does Not Span Two Clusters**

**target:** Analyst A

**steelman:** Analyst A claims that MM2 with KIP-618 cannot achieve true cross-cluster EOS because the source and destination have independent transaction coordinators with no shared two-phase-commit, and even KIP-618 only makes the destination-side produce transactional, not the end-to-end bridge.

**weakness:** Analyst A conflates two distinct failure modes and mis-characterizes KIP-618's scope. KIP-618 *explicitly states* it achieves "exactly-once delivery" for source connectors by writing source records and offsets atomically within a single destination-cluster transaction. The limitation Analyst A identifies—that the *source coordinator's* abort is not atomic with the *destination produce*—is a **real limitation**, but it applies only when a failure occurs *between* the source read and destination produce, not when replication completes nominally. More critically, Analyst A cites KIP-656 as "superseded" but provides no evidence that KIP-618 *failed* to address the original EOS goal; instead, KIP-618 *reframed* the problem: it achieves EOS for MM2 within the destination cluster (source records + offsets are committed atomically on the target), and delegates cross-cluster durability to MM2's operational deployment (dual-cluster architecture with idempotent sinks). The Strimzi article Analyst A cites states "transactions are only supported inside a single cluster," which is *true* but does not imply that MM2 cannot be architectured to provide end-to-end EOS *when deployed as two independent clusters*. Analyst A's implicit claim that KIP-618 is thus broken is unsupported—the KIP delivers what it promises within one cluster, and the cross-cluster boundary is a separate architectural choice, not a KIP-618 defect.

**evidence:** 
- KIP-618 search results state: *"With these changes, any source connector for which each source partition is assigned to at most one task at a time...should be capable of exactly-once delivery"* — this refers to delivery *to the destination cluster*, not end-to-end. ([KIP-618 search result](https://cwiki.apache.org/confluence/display/KAFKA/KIP-618:+Exactly-Once+Support+for+Source+Connectors))
- Kafka 4.1 geo-replication docs (verified) state EOS is supported "for dedicated MirrorMaker clusters" when `exactly.once.source.support=enabled` is set on the *target* cluster, confirming the scope is the destination write, not the source-to-destination bridge.
- The previous "My Response" analysis conflates "transaction markers not replicated atomically" (a true statement about distributed transaction semantics) with "MM2 EOS is broken" (an overstatement). MM2 EOS *within a cluster* is verifiable; cross-cluster EOS is not Kafka's responsibility—it is the application's (via idempotent deduplication).

**falsification:** Architect a two-cluster system where (a) source cluster has `acks=all, min.insync.replicas=2`, (b) MM2 runs with `exactly.once.source.support=enabled` on the destination, and (c) the consumer at the destination deduplicates using `(source_partition, source_offset)` as a key. Run chaos: kill the source cluster mid-replication, restart MM2, and measure duplicates on the destination. If duplicates are zero, Analyst A's severity is overstated. **severity:** **high** (not critical)

### **Finding 3: Producer State Eviction Causes Silent Idempotency Loss**

**target:** Analyst A

**steelman:** Analyst A identifies a real race in log segment deletion: when segments are deleted, producer state is evicted, and on the next produce, the broker returns `UNKNOWN_PRODUCER_ID`. The producer resets its sequence to 0 and retries, creating a duplicate window if the original request was written before deletion.

**weakness:** Analyst A does not adequately credit KIP-360's mitigation. KIP-360 (merged in Kafka 2.5) introduced **epoch bumping**, which *fundamentally changes* the semantics of a sequence-number reset. When `UNKNOWN_PRODUCER_ID` is returned, the producer does not merely reset sequence to 0; it increments its epoch and calls `InitProducerId` to register the new epoch with the broker. The broker then rejects any produce with the *old* epoch, so the old request—if it exists in the log—is guaranteed to have a lower epoch than the retry, preventing duplicates. KIP-360 documentation (confirmed in search results) states: *"If the epoch bump succeeds, the producer will reset sequence numbers back to 0 and continue."* The race window Analyst A describes is pre-KIP-360. For Kafka 2.5+, the protection is substantially stronger. Analyst A's finding is thus not "silent idempotency loss" for modern Kafka—it is a *known, bounded* state-eviction event that triggers re-registration and is handled safely. Analyst A rates this "high," but it applies only to Kafka < 2.5, which is obsolete (released 2020).

**evidence:**
- KIP-360 search results confirm epoch bumping on `UNKNOWN_PRODUCER_ID` (verified).
- KAFKA-12152 (confirmed in search results) addresses a residual gap: partitions without in-flight batches retain old sequence numbers after epoch bump, but the fix ensures the broker still rejects them under the old epoch.
- No evidence that modern Kafka (2.5+) exhibits the "silent loss" scenario Analyst A describes; instead, the scenario is *detected* (epoch mismatch) and *recovered* (retry with new epoch).

**falsification:** On a production Kafka 2.5+ cluster with default log retention, trigger log segment deletion (e.g., via force-delete or low retention), then send a produce that requires state re-registration. Verify that the LSO advances and no duplicates appear. If the test passes, Analyst A's severity should downgrade to "medium" or "low" (residual risk for pathological timing, not default behavior).

**severity:** **medium** (KIP-360 provides epoch-based protection; the risk is a residual gap in old Kafka or under pathological concurrent failures, not a default vulnerability)  
**confidence:** MEDIUM-HIGH (KIP-360's mitigation is verifiable, but the specific "silent loss" scenario is not explicitly tested in public Kafka benchmarks)

## Revised Acceptance Condition

4. **MM2 configuration** (if used): Enable `exactly.once.source.support=enabled` on the destination cluster; acknowledge that this guarantees EOS *within the destination cluster* for replication, not end-to-end across clusters.
