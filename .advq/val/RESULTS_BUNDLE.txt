**Finding 1: Race condition on concurrent duplicate requests**

- **steelman**: Redis SETNX (or SET NX) gives an atomic "set if not exists" primitive that prevents two sequential requests from both inserting a key; the second request sees the key and is rejected.
- **weakness**: Atomicity only covers the *key write*, not the full operation. If the implementation is CHECK → PROCESS PAYMENT → SET KEY, two concurrent requests with the same idempotency key can both pass the CHECK before either has written the key, both reach the payment processor, and both succeed — double charge. Even with SET NX at the front, if the key is set *before* the payment processor is called and the process crashes or times out before payment completes, the key exists but the payment did not; all retries are then silently dropped — lost payment.
- **evidence**: This is the canonical check-time-to-use-time (TOCTOU)
